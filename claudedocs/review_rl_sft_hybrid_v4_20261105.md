**RL 보상 기반 policy gradient와 오답노트 SFT 보조 손실은 구현돼 있다. 그러나 계획한 라운드형 GRPO/PPO의 핵심 확률 보정과 실행·평가 연결에 결함이 있어, 현재 코드를 유료 본학습 준비 완료로 판정할 수 없다.**

기존 CPU 검사를 통과하는 것과 아래 새 반례에 안전한 것은 다르다.

## 4. 본학습 전 고칠 결함과 검증 기준

### F1. 이전 정책 대신 현재 정책을 분모에 사용 — 높음

`error_note/rl.py:35–40`은 `group_loss(cur, cur.detach(), ...)`를 호출한다. 비율은 항상 1이라 PPO clip이 작동하지 않고 `mis_mask`도 호출하지 않는다.
라운드 전체를 먼저 생성한 뒤 여러 optimizer step을 하므로, 각 응답을 한 번만 사용하더라도 뒤쪽 응답은 현재 정책에서 생성한 것이 아니다.
이는 RL 기울기가 전혀 없다는 뜻이 아니라 **오래된 정책의 표본을 보정 없이 사용하는 정책 기울기**라는 뜻이다.

CPU 반례: 생성 당시 확률 0.2, 현재 0.8, advantage +0.5일 때 현재 구현 기울기는 −0.5이고 이전 확률로 clip한 기울기는 0이었다.
계획 §3.1/3.5/10.3은 old logprob·정책 차이 mask를 요구하지만 구현 부록은 current.detach로 바뀌었다고만 적었다.

기존 PPO 설계를 유지한다면 원래 토큰·생성 logprob와 정책 비율 보정이 필요하다. **현재 수정안은 §6의 단일 응답 REINFORCE로 대체한다.**
한 정책에서 수집한 작은 묶음을 한 번 갱신하고 끝내므로 PPO clip을 새 기본안의 필수 기능으로 넣지 않는다.
원래 토큰·실제 sampling 분포와 logprob의 일치, 오래된 정책의 표본 거부, microbatch 합 일치는 여전히 필수다.
기존 clip 반례는 과거 구현의 결함 증거로 보존한다.
근거: [TRL GRPO 설명](https://huggingface.co/docs/trl/grpo_trainer), [DAPO 논문](https://arxiv.org/abs/2503.14476).

### F2. RL이 원래 생성 토큰 대신 재토큰화한 텍스트를 학습 — 높음

`collect.py:748–750`, `collect_v4.py:79–88`은 원래 생성 ID·logprob를 유지하지 않고 text 중심으로 저장한다.
`train_v4.py:58`은 그 text를 다시 encode한다. decode→encode는 항상 역함수가 아니다.
캐시된 Qwen tokenizer로 만든 CPU 반례: `[49122,385]`→`hello`→`[14990]`.
이것은 실제 평가 응답이 바뀌었다는 사례가 아니라, 코드가 전제한 토큰 동일성이 보장되지 않는다는 반례다.

수정: collection→rows→encoder 전 구간에 원래 completion token IDs·실제 종료 토큰·정렬된 logprob·해시를 보존한다.
RL은 해당 토큰에만 보상을 적용한다. SFT의 문자열 target과 RL의 sampled actions를 구분한다.

### F3. 미완료 수집·자기검증과 오래된 노트 판정이 학습으로 이어짐 — 높음

- `rollout`이 2개의 오답까지만 남기고 중단돼도 다음 단계가 이를 ALL_WRONG으로 해석할 수 있었다. CPU 반례에서 note→resolve→A2/B가 생성됐다.
- `v4.py:196–203`은 어떤 claim의 probe가 비면 먼저 UNCHECKED를 반환한다. 다른 claim에서 이미 FALSE가 나왔어도 가려질 수 있다.
- 누락된 selfcheck도 `{}`/UNCHECKED가 되고 resolve는 진행한다. **정상 완료했지만 판단 불가인 경우와 실행 자체가 끝나지 않은 경우를 구별해야 한다.**
- gate가 기록한 note SHA를 원문과 대조하지 않아, 같은 교훈을 유지하고 노트 본문을 3 bars→99 bars로 바꾼 반례에서 예전 TRUE 판정으로 B행이 만들어졌다.

수정: 단계별 기대 ID/개수/완료 receipt/원문 해시를 다음 단계에서 필수 확인한다. 한 건의 FALSE는 불완전한 다른 probe에 가려지면 안 된다.
중단 재개는 같은 입력·모델·설정만 허용하며 완료 전에 학습 행을 만들지 않는다.

### F4. 교훈 누설 검사에 남은 구멍 — 높음

`v4.py:155`가 호출하는 `contract.hint_leak`의 보기 문자 검사는 대소문자에 민감하다.
gold=B인 CPU 반례에서 `Pick B.`는 FAIL, `Pick b.`와 `Choose the second choice.`는 PASS였다.
그대로 재풀이하면 정답 회복이 독립 해결처럼 기록될 수 있다.
별칭·약어 검사는 `--leak-terms`가 선택 사항이고 v4 Pod 계획에는 이를 넘기는 경로가 없다.

수정: 보기 지시 문맥에서 대소문자·괄호·서수/위치 참조를 검사하고 출처별 별칭 원장을 필수 연결한다.
일반 문장의 관사 a까지 막는 식의 과도한 정규식 변경은 피한다. 누설 양성·정상 교훈 음성 반례를 함께 검증한다.
새 수집 계약에서 고치고, 이전 결과를 소급 PASS로 바꾸지 않는다.

### F5. v4 Pod 계획을 기존 실행기가 거부 — 높음

`plan_v4.py:29–30`의 `note-v4-round`가 `notebook_rl/pod/job.py:37–40`의 허용 stage에 없다.
`job.py:188–189`에서 거부한다. 기존 stage 이름으로만 바꾸면 `chain.py:384–385`의 일치 검사와 충돌한다.

수정: job 허용 목록·chain 실행·receipt·pack/recovery를 같은 계약으로 연결한다.
검사: 계획 생성 검사에서 끝내지 않고, 실제 job validator→chain의 무료 CPU 전체 경로와 중단/회수 경로를 통과시킨다.

### F6. 2라운드 두 arm의 자료·스케줄과 평가 계약이 충돌 — 높음

`plan_v4.py:99–110,137–142`는 2라운드부터 각 arm의 자기 모델로 별도 자료를 만든다.
반면 `evaluate.py:137–139,147–154`는 두 arm에 같은 rows 해시·optimizer를 요구한다.
CPU 반례에서 다른 init+같은 rows는 통과했지만, 각자 올바르게 연결된 다른 rows를 넣으면 등록이 거부됐다.

`train_v4.py:123–127`의 schedule도 각자의 rows에서 계산된다. 같은 순서라도 hybrid 두 그룹(A1+B)은 2step,
control 한 그룹(A1)은 1step으로 달라졌다. README의 두 arm 스케줄 동일 주장은 2라운드에 일반화할 수 없다.

현재 §11은 F0와 사전 지정 HYB 한 모델 비교를 기본으로 한다. 평가기에는 이 모드를 명시적으로 추가해야 한다.
후속 별도 ablation에서 두 학습 arm을 운영한다면 arm별 rows/export lineage를 따로 등록하고 스케줄 차이도 기록한다.
서로 다른 표본을 같은 해시로 꾸미거나, 기존 3-arm 검사를 조용히 생략해 통과시키면 안 된다.

### F7. 재개 조건·RL 그룹 구성·로컬 기본값 — 중간~높음

- `collect_v4.py:362–375`의 identity에는 모델/export SHA·코드·엔진/정밀도·loop-stop·lesson-control·T1 원문 해시 등이 없다.
  출력 폴더만 재사용하면 다른 조건이 섞일 수 있다. 생성 설정·원본 이미지/actor·체크포인트 연결까지 고정한다.
- `train_v4.py:279–294`는 RL 일부 행이 인코딩 탈락해도 살아남은 행으로 학습한다.
  ±0.5 두 행 중 긴 음성 행만 탈락시킨 CPU 반례에서 RL 1행으로 COMPLETE 및 작은 모델 가중치 변경이 발생했다.
  원래 group membership/분모를 보존하거나 해당 그룹 전체를 거부해야 한다.
- `collect_v4 --engine hf`도 기본 `--max-num-seqs auto`일 때 vLLM의 GPU−16GiB 계산을 호출한다(`:412–415`).
  8GB 로컬은 시작 전에 거부된다. 현재 명령에는 **`--max-num-seqs 1`**이 필요하고, 기본값은 엔진별로 수정해야 한다.

## 5. 계획에 있으나 아직 끝나지 않은 부분

- 신규 adapter·3,500문항 pool-v4·군집 quota·10지 변환은 계획 부록이 S1로 명시적으로 유보했다. 구현됐다고 볼 수 없다.
- 제작자 도형/표 주석으로 노트 수치 주장을 독립 대조하는 §3.3 기능은 새 수집 경로에 없다.
- FULL 경로는 현재 `MISREAD + SELF_CONSISTENT`다(`v4.py:286`). 계획의 FALSE→교정 근거와 같지 않으며 내부 Vision 원인 증명도 아니다.
- 최종 8K 평가 연결은 있지만, 최종 32K/공식 이미지 조건·유지셋 중단·원하는 효과 판정이 모두 자동 연결된 것은 아니다.
- 파일럿 확대 기준이 서로 다르다: 계획은 한 곳에서 95% 구간, 다른 곳에서 점추정≥F0를 쓰고, 코드는 두 비교의 97.5% 구간 하한>0을 요구한다.
  실행 전에 하나로 고정한다. 실패한 뒤 문턱을 낮추지 않는다.

## 6. 바꿀 학습 방식: 단일 응답 RL + 자기 노트 SFT

### 6.1 한 문항의 경로와 단일 답 원칙

```text
정답 없는 P0·이미지 → T1 한 번 → 채점
  정답: 원래 T1 전체 풀이 내용 검사 → 수용된 원문만 양의 RL 보상 + A1 유지 SFT
  오답: gold를 보고 자기 노트 한 번 작성(고쳐 쓴 풀이 없음)
        → 내용·교훈 누설 검사
        → 통과한 교훈만 보고 gold 없이 재풀이 최대 한 번
        → 실제 정답·내용 검사 통과 시 A2와 B SFT
  검사 실패·재풀이 오답: 실패 보존, 추가 답 생성 없음
서로 다른 문항 한 묶음이 끝나면 RL+SFT 합산으로 한 번 갱신
```

- 평가에는 **각 문항의 첫 풀이 한 번**만 사용한다. 재풀이 회복률은 학습 진단이며 MMMU 정확도가 아니다.
- 학습도 `rollout=1`, `note≤1`, `resolve≤1`을 내부 계약에서 강제한다. CLI만 n=1로 바꾸지 않는다.
  best-of-N·다수결·첫 정답 선택·다중 seed·무교훈 대조 답 생성·여러 자기검증 중 좋은 판정 선택은 제거한다.
- A1은 정답·종료·길이·반복·전체 풀이 내용 검사를 통과한 첫 풀이, A2는 허용된 단 한 번의 재풀이 원문이다.
  A2도 정답·전체 풀이 검토를 따로 통과해야 한다. 둘 다 학습 입력은 **교훈 없는 P0**다.
  B는 모델이 직접 쓴 노트 원문이다. 틀린 풀이·gold·채점 결과는 B의 입력에만 두고 target 손실에서 제외한다.
- B 수용에는 원출처의 표·도형 주석 등으로 확인한 내용 근거가 필요하다. 자기검증의 TRUE나 재풀이 정답만으로
  노트 전체를 참이라고 하지 않는다. 독립 확인 불가 주장은 UNKNOWN으로 남기고 필수 주장이 미확정이면 B를 제외한다.
  모델이 쓴 글을 사람이든 다른 AI든 고쳐서 target으로 넣지 않는다. AI 검토는 `human_verified=false`다.
- Vision 경로의 자기 신고와 독립 관측 검증은 별도 기록한다. FULL을 썼다는 사실은 실제 시각 오류 원인 입증이 아니다.
  T1 RL/A1은 LM, 내용 검사를 통과한 A2/B는 노트의 `MISREAD` 자기 신고이면 FULL, 그 외에는 LM으로 고정한다.
  FULL은 Vision adapter+Merger+LLM adapter, LM은 Merger+LLM adapter다. 제거한 모델 probe의 `SELF_CONSISTENT`를 경로 조건에 남기지 않는다.

### 6.2 n=1에서 작동하는 RL과 확률 연결

현재 그룹 평균 GRPO를 n=1로 줄이면 모든 advantage가 0이다. 이를 **단일 응답 REINFORCE**로 교체한다.
최초 동결 SINGLE v1은 채점 완료한 T1에 `R=1(정답), 0(그 외)`를 사용했다. 실제 정답 풀이에 잘못된 설명이 있어도
양의 PG가 연결되는 반례를 확인했으므로, **이후 SINGLE v2는 `R=1(정답 + 원문 전체 검토 PASS), 0(그 외)`**로 수정한다.
baseline `b=0`은 유지한다. 이는 새 protocol/hash의 수정안이며 실행 중인 옛 동결 결과를 소급 변경하지 않는다.
내용 FAIL/UNKNOWN 또는 수용 근거가 없는 T1은 보상0으로 원래 묶음에 남는다. 반복·길이 때문에 A1 후보가 아닌 T1도
확인되지 않은 양의 보상을 주지 않는다. 필요한 검토의 WAIT 절차는 유지하며, 검토 누락을 자동 PASS로 바꾸지 않는다.
변조·오래된 검토 결합, 시스템 실패·채점 불가는 보상0으로 숨기지 않고 해당 묶음을 차단한다.

```text
L_PG = − sum_i [ R_i × sum_t log q_theta(original_action_it | original_prefix_it) ] / (B × C)
L_total = L_PG + λ_A1 L_A1 + λ_A2 L_A2 + λ_B L_B + L_KL
```

`B`는 사전 고정한 해당 묶음의 문항 수, `C`는 프로토콜에서 고정할 양의 상수다. 실제 응답 길이·맞힌 수로 분모를 바꾸지 않는다.
오답 또는 내용 미수용 T1은 보상항 0이지만 원래 문항 분모와 KL 범위에 남는다. 수용된 T1이 없으면 PG 신호가 없는 것이 정상이다.
SFT의 `L_A1/L_A2/L_B`는 각각 수용된 행별 target-token 평균 NLL의 행 평균이며, 해당 종류가 없으면 0이다.
이는 틀린 풀이를 정답 target으로 삼지 않는 기존 규칙을 유지하는 기본안이다. 음의 오답 보상·baseline 0.5는 현재 안에 넣지 않는다.
이 보상항의 양성 표본은 A1과 대부분 겹친다. 잘못된 설명을 강화하지 않는 대신 신호가 줄며,
내용을 확인하지 못한 실제 정답도 양의 보상을 잃는다. RL이 SFT보다 낫거나 별도 이득을 준다는 증거는 아직 없다.
방법의 근거는 [PyTorch 2.8 REINFORCE 설명](https://docs.pytorch.org/docs/2.8/distributions.html#score-function)이며, 이 프로젝트의 성능 증거는 아니다.

`q_theta`는 **실제로 표본을 뽑은 분포**다. temperature 0.7·top-p 0.8·top-k 20·presence penalty 1.5를 적용했다면
그 변환을 재현한 logprob를 써야 한다. raw `log_softmax`를 그대로 쓰면 다르다.
[vLLM 0.11.0 sampler 소스](https://raw.githubusercontent.com/vllm-project/vllm/v0.11.0/vllm/v1/sample/sampler.py)도 raw/processed logprob를 구분한다.
고정 버전에 없는 최신 기능을 있다고 가정하지 않는다. 기존 HF logprob collector도 temperature=1 지원만으로 이 조건을 검증한 것이 아니다.

필수 저장값은 원래 prompt/action IDs·실제 EOS·종료 이유·processed logprob·sampling 변환/정책/입력 해시다.
decode→encode와 EOS 재추정은 금지한다. 생성 당시와 backward 직전의 정책·지원 토큰 집합·logprob를 대조한다.
**정확한 replay를 구현하지 못하면 RL은 HOLD**다. greedy나 다른 sampling으로 자동 전환하지 않는다.

F0 안정화는 저장된 prefix에서 raw 전체 어휘 분포의 `KL(p_F0 || p_theta)`를 토큰·어휘 chunk로 계산하는 안을 사용한다.
정의는 `L_KL = beta × sum_i sum_t KL(p_F0(.|h_it) || p_theta(.|h_it)) / (B × C)`다.
범위는 모든 완료 T1의 생성 직전 prefix이며, prefix 자체는 gradient를 전달하지 않는 고정 문맥이다. 노트·재풀이에 중복 부과하지 않는다.
이는 관측 prefix에서의 조건부 정규화이며 전체 생성 경로 KL의 불편추정이라고 주장하지 않는다.
잘린 sampling 분포의 선택 토큰에 기존 k3 식을 붙여 정확한 raw KL이라고 부르지 않는다.
F0는 adapter뿐 아니라 원래 Merger도 유지해야 한다. 오답 token은 여기서 문맥일 뿐 정답 target이 아니다.
새 정규화의 메모리·속도와 성분별 크기를 로컬에서 확인한 뒤 `C/λ/beta/LR`를 동결한다.
기존 `λ_A2=.5, λ_B=.05, λ_A1=.05, beta=.02`는 출발 후보일 뿐 새 수식에서 검증된 값이 아니다.
성능 결과를 본 뒤 계수를 고르는 절차는 이번 파일럿에 넣지 않는다.

### 6.3 생성과 갱신을 묶는 단위

- **서로 다른 16문항 동안 같은 정책을 유지**해 T1·노트·재풀이를 끝낸다. microbatch별 backward를 모아 optimizer step을 딱 한 번 한다.
  다음 16문항은 새 정책으로 생성한다. 수천 문항을 먼저 생성한 뒤 여러 step으로 학습하는 기존 라운드 방식은 사용하지 않는다.
- 같은 HF 정책 객체에서 생성과 학습을 순차 수행하는 경로를 먼저 검증한다. 동시에 두 엔진을 GPU에 올리지 않는다.
  vLLM은 매 묶음의 정책 동기화·확률 일치·export/교체 시간까지 입증한 뒤 선택한다. 기존 대량 생성 속도가 이 방식의 속도는 아니다.
- RL 표본은 한 번만 사용한다. SFT 종류가 없으면 그 항은 0이며 다른 항에 가중치를 재분배하지 않는다.
  모든 손실이 0인 묶음은 AdamW decay만 실행하지 않는다. 문항/예정 LR 구간은 소비하되 실제 optimizer update 수는 늘리지 않는다.
- 파일럿 300은 `18×16+12`로 19구간, 후속 3,200은 200구간이다. **총 219개의 예정 갱신 구간**이며 실제 update가 219라고 미리 쓰지 않는다.
  파일럿 시작부터 전체 LR horizon을 고정하고 optimizer moments·LR 위치·RNG·data cursor를 이어간다.
  현재 `train_v4`의 라운드별 optimizer 초기화는 수정 대상이다. 파일럿 뒤 프로토콜을 바꾸면 새로운 실험이다.

### 7.2 확보 우선순위와 품질 기준

1. `notebook_rl/adapters/hf_registry.py`의 기존 변환기를 먼저 재사용한다. AI2D/TQA, ChartQA/PlotQA,
   FinQA/TATQA/TATDQA, VQARAD 등에서 실제 이미지가 필요한 문항과 원출처 annotation이 있는 문항을 조사한다.
   데이터셋 이름만으로 모든 문항이 시각 추론 학습에 적합하다고 보지 않는다.
2. 부족한 회로·투상도·악보 분야는 CircuitVQA·TriView2CAD·MusiXQA 등 **후보**의 실제 공급과 사용 조건부터 확인한다.
   EXAMS-V·MMK12·UniGeo/GeoQA+·PathVQA·MMSci도 후보이며, 사용 가능·라이선스 적합·오염 없음이 확인된 자료로 표기하지 않는다.
   HF 등록명보다 원 제작 출처와 벤치마크와의 공유 계보가 중요하다.
3. 원 제작자의 학습 split, 고정 revision, 라이선스/다운로드 조건, 사람·프로그램 정답, 원래 이미지와 질문 연결,
   선택지·단위·허용 답 별칭을 확인한다. 해설 이미지·정답 표시·깨진 이미지·빠진 참조·모호한 gold는 제외한다.
   상위 모델 rationale/distillation 자료는 사용하지 않는다. 텍스트 전용 문제를 억지 이미지로 만들어 넣지 않는다.
4. 원출처 난도·연산 단계·시각 관계·이미지 수·답 유형으로 난도/형태를 기록한다. 짧은 출력이나 낮은 정답률을 어려움의 증거로 삼지 않는다.
   숫자·축·단위·좌표·도형 관계처럼 독립 검증 가능한 annotation을 함께 가져와 노트 내용 감사에 활용한다.
5. 질문 원형을 유지한다. 이 1차 안에서는 무리한 10지 변환·패러프레이즈·임의 수치 교체를 넣지 않는다.
   원래 제공된 다지선다·수치·짧은 답·단일/복수 이미지를 섞고 유형별 채점 계약을 고정한다.
   SFT의 32토큰 하한도 답 유형과 무관하게 적용하지 않도록 수정한다. 길이 대신 정답·종료·내용·원문 무변조를 검사한다.

`gold_supported`의 근거는 **원 제작자의 실제 annotation, 해당 원본 이미지와의 연결, 변환된 질문·선택지에 대한 정답 지지**다.
변환된 gold끼리 일치하거나 `HUMAN` 표기가 있다는 사실만으로 통과시키지 않는다. native ID/파일 hash/원본 주석을 직접 대조하고,
질문의 “주된 조직/주된 재료” 같은 표현까지 주석이 뒷받침하는지, 복수 보기가 함께 정답이 되는지 확인한다.
병리·식물종·약리 역할의 원출처 라벨 검증과 검토자가 사진만으로 독립 진단하는 것은 구분한다.
후자의 전문성 부족을 라벨 오류율로 보고하지 않지만, 원출처 근거로도 질문의 정답을 확인하지 못하면 계속 UNKNOWN/부적격이다.
예비 시각 검토에서 UNKNOWN이었던 항목을 새 원출처 근거로 재판정할 때는 **이전 의견을 보존한 별도 근거·판정**을 남긴다.
표본 순서, 20→60 확대 조건, 실패 허용 개수는 바꾸지 않는다.

추가로 최종3,500개 모두의 원래 정답을 해당 학습 채점 계약에 넣어 자기 일치가 되는지 CPU에서 검사한다.
이는 모델 성능 검사가 아니라 채점기·자료 인터페이스 검사다. 원출처에서 확인한 단위·변수·scale의 대표 표기도 시험한다.
11,483개 후보를 점검했을 때 ChartQA의22개 정답 문자열은 `/` 또는 `or`를 포함해 현재 파서가 그대로도 수용하지 못했다.
이22family는 `CONTRACT_UNSUPPORTED`로 별도 제외하며 라벨 오류·MMMU 중복으로 표시하지 않는다.
기하의 이미지 단위와 명시적인 Find-variable 대상은 원본 질문/이미지에 결합한 규칙으로 준비한다.
정답·허용오차를 바꾸거나 단위를 무조건 제거해서 통과시키지 않는다. 자기 일치 통과만으로 모든 모델 출력 형식을
지원한다고 주장하지 않으며, 필수 형식의 근거가 없으면 유료 실행 전에 HOLD한다.

### 7.3 선정·분리·동결 순서

```text
출처/revision/라이선스/원본 split 확인
 → 목표보다 넉넉한 후보 취득·공통 adapter 변환
 → 품질 제외·family 연결·기존 held-out 보호
 → §8의 로컬 MMMU/MMMU-Pro 전수 중복 검사·경고 판정
 → 허용된 후보에서 군집/출처 quota와 고정 hash 순서로 3,500개 선정
 → 군집별 파일럿 quota를 만족하는 300개를 맨 앞에 고정, 나머지 3,200개를 교차 배치
 → 최종 order까지 재검증 → manifest·검사 영수증·학습 bundle 동결
```

- 후보 순서는 기존 `hf_common.candidate_order`의 seed/source/native_id 기반 hash를 재사용한다.
  군집 안에서도 정답 라벨이나 모델 결과로 우선순위를 정하지 않는다. 후반이 몇 출처에 몰리지 않게 순서를 고정한다.
- 가족·원본 이미지·문항 계보 기준으로 train/dev/sealed를 분리한다. `hf_common.split_for`의 기존 4분할 계약을 조용히 바꾸지 않는다.
  기존 dev 402/sealed 209는 과거 기록이며 실제 ID·해시를 확인해 보호한다. 새 원본의 파생 family를 train으로 옮기지 않는다.
  부족한 외부 검증 자료는 별도 held-out으로 확보하며 3,500개에서 임의로 떼어 수량을 줄이지 않는다.
- **현재 `pool_freeze.freeze`는 shortfall을 기록하고도 FROZEN을 낼 수 있다.** `category_map`만으로 군집/출처 상한이 강제되지 않는다.
  또한 `error_note/order.py`는 중복 구조를 제거할 수 있으므로 freeze 이전뿐 아니라 **최종 order에서 정확히 3,500개**인지 확인한다.
- `train=3500`, `pilot=order[0:300]`, `main=order[300:3500]`, 고유 ID 수·군집 합·출처 상한·held-out 교집합 0을 모두 만족해야 완료다.
  부족하면 로컬에서 부족 분야 후보를 추가 조사한다. 기준을 낮추거나 임의 분야로 채우지 않고, 구성 변경은 새 선정안을 남긴다.
  **현재는 이 3,500문항이 선정·동결됐다는 증거가 없다.**

## 8. 중복 검사는 로컬, RunPod는 검사된 자료의 동일성만 확인

### 8.1 로컬 감사 범위와 판정

기존 `build_exclusion_index` → `hf_pool_exclusion`의 `registry/engines/assemble` → `hf_pool_review`의 경고 판정
→ `hf_pool_exclusion apply` → `pool_freeze` 순서를 재사용한다. `apply`에는 검토 결정 파일이 먼저 필요하다.
현재 고정 `benchmark_inventory_v1.json`의 기대 범위는 **100파일·16,740레코드**다.
MMMU dev/validation/test 및 MMMU-Pro standard10/standard4/vision을 포함한다. Pro 최종 평가는 standard10이지만 제외 검사는 더 넓게 한다.
이 숫자는 고정 inventory 범위이며 앞으로 존재할 모든 revision까지 검증했다는 뜻이 아니다.

- 파일/원본 ID·이미지 exact hash, 텍스트·OCR, perceptual hash, SSCD/SigLIP 유사도, 원출처·family 연결을 기존 고정 기준으로 검사한다.
  일부 이미지나 benchmark split이 없으면 검사 완료로 처리하지 않는다. 기존 임계값·coverage 검사를 완화하지 않는다.
- 경고는 실제 문제·이미지를 대조해 DISTINCT/DUPLICATE/UNRESOLVED로 기록한다.
  DUPLICATE와 UNRESOLVED는 같은 family까지 제외한다. 미검토 후보를 자동 DISTINCT로 바꾸지 않는다.
- benchmark는 **제외 신호에만** 사용한다. benchmark 문제·정답·풀이·전사·수치 변형을 학습기로 전달하지 않는다.
- 보고 표현은 “고정 검사 범위에서 허용된 3,500개, 중복/미해결 후보 제외 완료”다.
  유사도 검사가 잡지 못한 공유 출처까지 포함해 절대 중복 0을 증명했다고 주장하지 않는다.

### 8.2 교수님이 원할 때 실행할 별도 위치 — 진입점 구현, 실제 감사 진행 중

```text
fine_tuning/data_audit/              # 기존 엔진을 호출하는 선택 실행 진입점
  README.md                         # 범위, 필요한 로컬 원본, 재현 순서, 결과 읽는 법
  __main__.py                       # 명시 호출 때만 기존 감사 CLI로 연결
fine_tuning/notebook_rl/            # 기존 검출기·freeze·검증 helper는 유지
fine_tuning/error_note/             # 학습은 frozen approval + 자료 해시만 검사
```

새 중복 검출 엔진을 만들거나 기존 해시 고정 파일을 옮기지 않는다. 별도 진입점은 기존 검사 코드를 호출하는 최소 연결부다.
학습 import/startup에서 이 감사를 자동 실행하지 않는다. 선택 설치 항목과 필요 자원을 README에 표시한다.
교수님은 자신의 로컬 benchmark cache와 외부 자료를 지정해 재검사할 수 있다.
이 경로는 구현했고 CPU 연결 검사를 통과했다. 아래는 도움말 확인 명령이며, 실제 자료의 감사 완료 증거는 별도 영수증으로 확인한다.

```bash
python -m fine_tuning.data_audit index --help
python -m fine_tuning.data_audit exclusion --help
python -m fine_tuning.data_audit review --help
python -m fine_tuning.data_audit pool --help
python -m fine_tuning.data_audit export-approval --help
```

GitHub에는 코드·설명·정책·정제한 통계만 게시한다. 원본 문제/이미지/정답·benchmark index·OCR/embedding·review packet은 로컬 private 경로에 둔다.
특히 `exclusion_bundle`의 `evidence.json`에는 benchmark OCR/embedding이 들어갈 수 있으므로 학습 bundle에 넣지 않는다.
파일 경로를 차단하는 것만으로 내용 누출이 검증되는 것은 아니다.

### 8.3 이미 있는 hash-only 경로를 학습 실행기에 연결

`notebook_rl/local_run.py:frozen_approval_output/_frozen_vault`는 **`frozen-approval-verify-v1`**을 이미 구현한다.
저장된 로컬 승인 영수증·코드·union receipt·manifest·record/image hash를 확인하며 benchmark index/검출기를 다시 열지 않는다.
`pod/chain.py`에도 `--frozen-approval`, `--frozen-approval-sha256` 전달 경로가 있다. 새 인증 체계를 만들지 말고 이를 연결한다.
단, 이 영수증은 자료의 검사 상태이며 유료 실행·가중치 갱신의 사용자 승인을 대신하지 않는다.
`approval.code_hashes`가 읽는 `notebook_rl` Python 소스는 clean clone에 유지한다. 제거할 것은 benchmark 원문/index와 OCR·embedding 엔진 artifact다.
이 해시 범위 밖의 `error_note` 및 새 `data_audit` 소스는 job의 clean commit/source binding으로 별도 고정한다.

동결 자료와 실행 명세에 다음을 묶는다.

| 묶을 내용 | 필요한 이유 |
|---|---|
| 출처/revision/라이선스·학습 split·family·train/dev/sealed ID | 출처·분리 재현 |
| detector/code/config/calibration/index inventory hash·coverage·경고 판정 요약 | 어느 검사에서 허용됐는지 확인 |
| actor/verifier/lineage 및 이미지 byte hash·union receipt·manifest | 문제·gold·이미지의 변경 탐지 |
| 고유 train 3,500·군집/출처 합·ordered-ID hash·pilot 300 prefix | 누락·다른 문제·중복 학습 차단 |
| clean code commit·고정 protocol·model/export·실행 slice | 다른 정책/코드/자료가 섞인 재개 차단 |

RunPod는 **모델을 올리기 전에** 이 영수증의 사전 등록 SHA와 bundle hash, 정확한 개수·순서·subset·held-out 비포함만 확인한다.
bundle 안에서 새로 계산한 자체 SHA끼리만 비교하지 않고 로컬에서 고정해 job에 전달한 예상값과 비교한다.
벤치마크 원문/index·OCR/embedding 검출기를 내려받거나 `approval._validate`의 전체 감사를 다시 호출하지 않는다.
학습용 bundle은 허용된 외부 자료와 필요한 최소 manifest/영수증만 포함한다.

자료·정답·이미지·가족 분리·검사 규칙을 바꾸면 기존 동결을 무효화하고 **로컬에서** 다시 검사/동결한다.
무관한 학습 코드만 바뀐 경우에는 기존 검사 증거를 보존한 채 코드와 승인 영수증의 연결을 로컬에서 다시 확인한다.
검사를 건너뛰는 범용 `--skip-contamination` 옵션은 만들지 않는다.
**중복 전수검사를 생략하는 것이지, 매번 생성되는 노트의 내용·누설·채점 검사를 생략하는 것은 아니다.**

## 10. 로컬에서 반복할 검증 사이클

### 10.1 실행 단계와 통과 조건

| 단계 | 실행 | 통과 조건·한계 |
|---|---|---|
| L0 계약 고정 | §6의 단일 응답·보상·마스크·정규화·시간/자원한도 정의 | 금지된 생성/후보 선택 경로가 없음. 프로토콜·코드 SHA 기록 |
| L1 CPU 원인 수정 | F1–F7 반례를 보존하고 기존 helper/호출부에서 수정 | 수정 전 실패→수정 후 통과, 기존 회귀도 통과 |
| L2 CPU 통합·복구 | 작은 모델/fixture로 plan→자료검사→수집→rows→loss→저장/재개→회수 연결 | 아래 장애 주입에서 가짜 COMPLETE·중복 생성·부분 학습 없음 |
| L3 실제 NF4 고정 2문항 | 실제 Qwen4B, HF 동시 1, P0→채점→노트→허용 시 재풀이 | 원문·actions·확률·gold 경계가 연결됨. 실패도 원래 상태로 보존 |
| L4 같은 고정 목록을 총 10문항까지 | 완료된 첫 2개를 재사용하고 **다음 8개만** 처리 | 성공 문항 교체·재추첨·추가 seed 없음. source/이미지 유형별 관측 기록 |
| L5 실제 NF4 무갱신 backward | T1 PG, KL, A1/A2/B를 각각 계산·역전파 후 grad clear | 유한 기울기·필수 성분 증거·전후 parameter/NF4 hash 동일, optimizer0/scheduler0/weights_saved=false |
| L6 재감사 | 실제 출력의 문제 원인 분석→최소 수정→관련 CPU→새 source-bound 검사 | 핵심 반례 닫힘, 필수 경로 누락은 HOLD, 기존 v3 증거를 새 v4 PASS로 승격하지 않음 |
| L7 실제 1step·fresh reload | 실제 Qwen 갱신/저장 허용을 받은 뒤 별도 실행 | 현재 HOLD. 별도 PID에서 weights·optimizer·scheduler·RNG·cursor·forward/probe 검증 |

현재 제한은 **실제 Qwen 가중치 무변경과 RunPod 보류**다. 작은 CPU fixture의 갱신은 가능하지만 실제 Qwen 갱신 증거가 아니다.
L3–L5는 원래 토큰에 RL/SFT 손실과 기울기가 연결되는지 확인할 수 있다. 실제 update·재로딩까지 완료했다는 표현은 L7 이후에만 쓴다.
초기 정책이 F0와 같으면 KL과 KL 기울기가 0인 것이 정상이다. 양의 KL/비영 기울기는 CPU에서 정책을 바꾼 검사와 L7 이후에 확인한다.

실제 오답 교정 경로의 완료 증거는 **같은 문항**에서 다음 연결이 모두 있어야 한다.

```text
실제 INCORRECT T1
 → 모델 자신이 쓴 노트 + 내용/누설 검사 통과
 → gold·원노트 없이 허용 교훈으로 단 1회 재풀이 CORRECT
 → 힌트 없는 P0 입력의 A2 및 같은 노트 B
 → A2와 B 각각 실제 backward, 원문/입력/target SHA 연결
```

처음부터 맞은 A1이나 단순 답 누락/잘림 회복으로 이 경로를 대신하지 않는다.
RL 보상항도 **KL과 분리한 실제 유한·비영 기울기**가 필요하다. 현재 b=0에서는 정답 T1이 그 증거를 제공한다.
고정 10문항에 필요한 경우가 안 나오면 해당 성분은 미검증이다. 더 볼 필요가 있으면 다음 연속 구간·한도를 먼저 등록하고,
정답이 나온 경우만 모아 검증 목록을 새로 만들지 않는다.

### 10.2 매 사이클에서 확인할 구체적 항목

- **입력:** 첫 풀이·평가에는 gold/노트가 없음. 노트 입력에서만 gold 제공. 재풀이에는 누설을 통과한 교훈만 제공.
- **행/마스크:** RL actions가 원래 IDs와 동일하며 prompt·이미지 placeholder·padding 손실은 0.
  잘림/반복 종료에 EOS를 만들어 넣지 않음. A2 target에 교훈/평가자의 설명이 없음. B target은 실제 노트 원문뿐임.
- **확률:** original policy/processed logprob와 replay가 사전 허용오차 내 일치. dropout·sampling processor·이미지 처리도 동일 계약.
  정규화와 microbatch 분할 전후 결과 일치. 지원 밖 token·NaN/Inf·오래된 정책 표본은 차단.
- **학습 신호:** PG/KL/A1/A2/B 각각의 행 수·loss·기울기 norm을 기록. 종류가 하나 없는데 전체 PASS하지 않음.
  LM 경로의 Vision gradient 없음, FULL의 선언된 L/M/V 경로 확인. 경로별 관측이 없으면 그 경로는 미검증.
- **원문 내용:** note가 실제 T1 오류를 지적하는지, source 근거와 맞는지, 교훈이 일반화 가능한지 검사.
  “형식이 맞음/자기검증 TRUE/재풀이 정답” 세 가지를 내용 정확성과 동일시하지 않음.
- **불변성:** no-update 전체 parameter·동결 NF4 상태 hash, F0 Merger/adapter 복원, grad clear를 확인.
  무갱신에서는 정책 변화 이후의 실물 동작을 확인할 수 없으므로 그 부분은 CPU 및 L7로 분리.
- **비용:** 생성/노트/재풀이/backward별 시간·token·최대 VRAM/RAM, 승인되지 않은 CPU/disk offload 없음,
  긴 정상 풀이와 반복 종료를 구분. 단축 설정을 쓰면 별도 진단이며 본학습 8K 경로 검증을 대체하지 않음.

각 실행은 `문제·코드·protocol → 실제 raw/action → 판정 → 행 → 성분별 기울기 → 종료 receipt`를 남긴다.
수정 뒤 재실행은 새 source/protocol로 구분하고 이전 실패를 보존한다. 이전 성공 출력과 새 출력 중 좋은 답을 고르지 않는다.
동일 원인의 수정·검증은 최대 3회다. 해결되지 않으면 원인/설계 차단으로 보고하고 무근거 반복이나 유료 이전을 하지 않는다.

## 11. RunPod 진행 순서·300문항 판정·예산

### 11.1 유료 실행 진입과 300→3,200 연결

로컬 데이터 동결 + L0–L6 완료 + 실제 갱신을 허용한 L7 검증 뒤, 사용자가 RunPod 보류를 해제하면 진행한다.
계획/receipt가 존재한다는 이유만으로 실행하지 않는다. 첫 실행은 MMDL_test의 고정 clean commit·고정 lock에서 설치한다.
외부 학습 자료 bundle은 별도 경로로 회수/취득하고, 로컬 코드·venv·모델 cache를 업로드해 덮어쓰지 않는다.

1. 고정 자료/영수증/순서를 hash-only로 확인한다. **MMMU/MMMU-Pro 중복 검색·자료 재선별은 하지 않는다.**
2. CUDA/BF16·이미지·모델·메모리·확률 replay 및 승인된 최소 갱신/재로딩을 제한된 smoke로 확인한다.
   로컬 NF4는 호스트 UVM/CUDA·BF16/vLLM 수치·48GB 처리량·원격 storage 장애까지 증명하지 못한다.
3. smoke 가중치를 버리고 사전 지정 F0에서 **고정 300문항**을 학습한다. 500문항 확대나 표본 교체는 하지 않는다.
   최종 파일럿 checkpoint 하나를 외부 dev의 첫 답 1회로 F0와 비교한다. 같은 질문에서 후보를 골라 점수를 올리지 않는다.
4. 아래 확대 gate와 비용 gate를 통과하고 본학습 승인이 있으면 같은 checkpoint/optimizer 상태에서 **나머지 3,200문항만** 이어간다.
   300을 다시 포함한 3,500개 학습을 추가하는 방식이 아니다. 파일럿 실패 시 확대하지 않는다.
5. 최종 checkpoint 하나를 사전 등록 조건으로 평가하고, 결과/가중치 회수·hash 확인 뒤 소유 자원을 정리한다.

### 11.2 파일럿 gate와 성능 주장

기본 비교는 **F0 + HYB 하나**다. RL-only 추가 학습/생성과 동일 문항 무교훈 재풀이는 기본 비용에 넣지 않는다.
따라서 이 실험만으로 RL과 노트 SFT의 개별 인과 기여를 분리했다고 주장할 수 없다.
평가기의 기존 NOTE/NO-NOTE/F0 강제와 97.5% 두 비교 gate는 새 명시 모드로 바꿔야 한다.

파일럿을 돌리기 전에 고정할 **확대 판단 규칙**은 다음과 같다.

- 기능/자료/확률/필수 기울기 검사 통과, 시스템 실패·누락 0.
- 사전 고정 외부 dev에서 HYB 정답 수가 F0보다 많고, 별도 표시한 유지 부분집합에서 정답 수가 F0 이상.
- 같은 dev에서 최종답 누락 수와 토큰 상한 도달 수가 각각 F0 이하. 출력 길이·반복·노트/A2 수용률도 함께 보고.
- 측정한 잔여 token/시간·저장/회수 비용이 남은 예산 안에 들어옴.

모든 항목을 만족해야 확대 후보로 삼는다. 파일럿 후 문턱을 낮추지 않는다.
정답 변화는 문항별 paired 차이와 **95% 구간**을 함께 보고한다. 위 점추정 기반 gate 통과는 돈을 더 쓸지 정하는 판단이며 개선 입증이 아니다.
구간이 0을 포함하면 불확실하다고 명시한다. sealed는 파일럿 선택에 쓰지 않는다.

최종 목표는 70%=630/900이다. B2 558보다 +72, 과거 8K F0 541보다 +89이며 공식 67.4% 초과는 최소607개다.
이 계산은 예상 성능이 아니다. 8K/낮은 이미지 budget 실험과 32K/공식 이미지 B2를 동일 조건 학습 효과로 비교하지 않는다.
최종 62/67.4점 비교를 주장할 protocol은 사전에 고정하고, 적합한 F0 비교 실행이 없으면 그 평가 비용도 포함한다.
MMMU의 문항별 실패를 이용해 새 학습 문제를 골라내지 않는다. 기존 validation은 이미 반복 관측됐음을 보고하고 test/pro sealed 최종 평가와 구별한다.

### 12.1 실제 구현·원본 품질 검토 후 추가된 근거

- 새 단일 응답 경로의 통합 CPU **87검사 통과**, 변경 경로 Ruff 통과. 보호 대상 7파일의 byte hash 불변을 확인했다.
  단일 경로는 짧은 정답을 길이만으로 버리지 않도록 최소 1토큰으로 바꾸되 빈 출력·반복·내용 검토를 유지한다.
  과거 v4의 기본 32토큰 조건은 그대로다. 단일 경로의 판단을 과거 실행에 소급 적용하지 않는다.
- 실제 NF4 실행용 소스 539파일(11,498,095byte)을 별도 동결했다. 기존 자료의 새 승인 export와
  동결 소스에서의 hash-only 재검증을 통과했고, 첫 10문항의 원출처 자료를 별도로 준비했다.
  고정 첫 2문항의 실제 Qwen NF4 풀이·노트 생성을 완료했다. ScienceQA 첫 풀이는 오답(214토큰·28.84초),
  ChEBI는 잘림(8,192토큰·1,346.51초)이었다. 두 노트는 각각 279/253토큰으로 끝났다.
  ScienceQA 노트는 원래 잘못 알았던 새의 식성을 계속 잘못 주장했고, ChEBI 노트는 구조에 없는 ethoxy와 steroid 골격을 주장했다.
  정답을 받은 뒤 쓴 노트도 사실 검증을 통과하지 못할 수 있다는 실제 사례다. 원문을 고치거나 수용 판정을 대신 넣지 않는다.
  이 기록만으로 RL/SFT 역전파·전체 오답노트 사이클 통과를 주장하지 않는다.
- 새 후보 전수 특징 추출은 오류 0으로 종료했다. SSCD/SigLIP 이미지 각각 19,158개, SigLIP 텍스트 54,029개,
  OCR 16,900개는 benchmark와 후보를 합친 해당 엔진 입력 수이며 **학습 문항 수가 아니다**.
  전수 유사도 대조도 종료했으며 경고 판정이 남아 있다. 이전 검토와 경고 내용까지 정확히 같은 후보 10,361건만 재사용 검증 대상이다.
  같지 않은 경고 61건을 과거 DISTINCT 판정으로 덮지 않는다. GPU 특징 추출이 끝난 뒤에만 Qwen을 올렸다.
- subject quota만으로는 출처별 재사용/신규 quota와 C3/C8의 같은 과목 배정을 고정할 수 없어,
  `pool_freeze`에 **명시한 ID·군집 영수증을 선택적으로 받는 경로**를 추가했다.
  제외·held-out·미해결 문항은 선택할 수 없고, 선택하지 않은 적격 문항은 품질 실패가 아니라 `EXCLUDED_QUOTA`로 남긴다.
  옛 기본 경로의 세 출력 파일이 byte 동일함을 확인했다. 독립 검토에서 발견한 영수증 본문/SHA 재연결 및 marker 누락 결함을 수정했다.
  수정 뒤 집중 14검사, 실제 freeze→materialize→approval→원본 index 제거 후 hash-only 연결 검사 1개,
  독립 검토 4검사와 ID/군집 동시변조 반례가 통과했다. 서로 겹치는 검사를 고유 검사 수로 합산하지 않는다.

### 12.2 원출처 추가 대조와 실제 공급 부족

예전 검토와 정확히 일치하는 경고만 재사용한 잠정 계산에서는 학습 후보 3,817행/3,770family가 남는다.
이 중 이전 학습 native family는 2,654개, 실제 신규 family는 1,115개다. 따라서 **기존 1,320+신규 2,180 목표에서
신규가 1,065개 부족**하며, 품질·군집 조건을 더 적용하기 전의 수량이다. 3,500개 단순 합계만 보고 완료할 수 없다.
별도로 새 ChartQA/Geometry3K/MapQA/SSMR 각 5family의 실제 비교쌍 20개를 이미지·질문으로 검토해 DISTINCT 의견을 남겼다.
이는 개별 검토이며 나머지 경고를 일괄 해제하거나 검출 임계값을 낮춘 것이 아니다.

- **NCT-CRC 질문 변환 오류:** `hf_pathology.py`의 기존 질문은 모든 이미지를 대장 조직이라고 설명한다.
  원 제작자는 정상 조직에 위 절제 표본을 포함했다고 명시한다. 따라서 원래 class 정답이 맞더라도 추가한 장기 설명은
  모든 행에서 지지되지 않는다. 새 변환에서는 장기를 단정하지 않는 질문으로 고치고 이미지·native ID·정답은 유지해야 한다.
  새 actor/source hash와 새 감사가 필요하며, 실행 중인 동결 NF4 자료와 옛 검토는 바꾸지 않는다.
  [제작자 데이터 설명](https://zenodo.org/records/1214456),
  [원 논문의 자료 구성](https://journals.plos.org/plosmedicine/article?id=10.1371/journal.pmed.1002730).
- **DeepWeeds 질문 의미·분할 미확정:** 원 논문은 사진에 여러 잡초 종이 있을 수 있다고 설명한다. 원래 라벨의 종 존재와
  변환 질문의 “main plant”는 같은 조건이 아니다. 20개 원본 CSV/이미지 연결을 확인해도 10개는 이 참조가 미확정이었다.
  HF의 train에는 전체 17,509개가 들어 있어 제작자의 별도 교차검증 fold에 따른 train 소속도 아직 확인되지 않았다.
  수량을 위해 통과시키지 않고 선정안에서 대체할 자료를 조사한다.
  [제작자 논문](https://www.nature.com/articles/s41598-018-38343-3).
- **전문성 UNKNOWN의 별도 재검토:** 원 제작자 이미지·주석을 추가로 확인한 PlantVillage 20개는 원출처 기반 정답이 지지됐다.
  ChEBI는 CID/SMILES/이미지/curated role과 선택지를 대조해 19개 지지, 1개는 histamine/H2 역할 범위가 미확정이다.
  예비 시각 의견을 삭제하지 않았으며 이 결과만으로 출처 수용을 완료하지 않았다.
- **추가 확보 방향:** 회로 후보의 일부를 원 제작자의 CLEVR 공간 관계 문항으로 대체하고, 축소된 문서 cache는
  원본 TAT-DQA PDF의 충실한 페이지 렌더링으로 대체하는 경로를 준비한다. 어려운 분야를 쉬운 분류 문제로 채우지 않는다.
  실제 품질·분리·중복 판정과 source/family 수량을 확인한 뒤 수정된 선정안을 고정한다.

첫 NF4 2문항에서 거부된 노트는 재생성하지 않았다. 고정 10문항의 첫 풀이 생성은 완료했지만,
기하 문항의 채점에서 `UNVERIFIABLE`로 중단됐다. 원본 그림의 95°·109°·33°·24° 표시를 직접 확인했고,
모델의 최종 `123°`와 원래 숫자 정답 123을 비교할 도 단위 규칙이 누락된 것이 원인이다.
기존 숫자 허용오차와 정답은 유지하고, 해당 원본 이미지에 결합된 단위 관측을 별도 규칙 버전으로 기록한다.
옛 동결 소스·원문·실패 기록을 보존하며, 완료된 10풀이와 2노트의 원장을 그대로 검증·재사용하는 별도 출력으로 복구한다.
이는 같은 문제를 다시 풀어 답을 고르는 실행이 아니다. 실제 확률 replay와 성분별 기울기 검사는 아직 남아 있다.
메모리별 동시 처리도 측정한 용량에 맞추는 경로를 구현 중이며,
아직 측정하지 않은 동시 수나 BF16 처리량을 검증 완료로 표시하지 않는다.

CLEVR 원본 train에서 1,000이미지·10,000질문/program·1,000scene을 확보했고, 원본 program 실행과 답이
10,000개 모두 일치했다. 기존 mirror 500이미지는 원본 archive와 byte 동일함을 확인했다.
TAT-DQA는 원본 PDF 페이지를 렌더링하는 별도 경로로 준비했다. 실제 renderer 시험에서 발견한 page 수명관리 오류를
수정하고 실제 2페이지 시험 및 native 페이지 렌더링을 확인했다. 원래 보고서 단위의 held-out 분리를 유지하면
새 train 후보는 103report family뿐이다. 두 출처 모두 최종 시각 품질·전수 중복 검사를 통과한 3,500개 선정 결과는 아니다.

### 12.3 실제 복구 및 추가 품질 검토에서 확인한 제한

단위 규칙을 보완한 뒤 저장된 첫 풀이 10개를 **생성 호출 0회로 재채점**했다. 기하 문항만
`UNVERIFIABLE → CORRECT`로 바뀌었고 나머지 9개는 동일했다. 독립 검토는 옛 동결 코드로
10풀이·2노트 요청을 다시 구성해 모두 원장과 일치함을 확인했다. 재개 실행에서는 이 12개를 그대로 쓰고
미실행 상태였던 지도 문항 노트 1개만 생성했다. 가중치 갱신·저장은 없다.

현재 첫 풀이 결과는 정답7/오답1/잘림1/최종답 형식 실패1이다. 지도 노트는 색 범위의 하한만 답한 오류를
올바르게 지적했지만, 원래 최종답이 있었는데 원인을 `NO_FINAL_ANSWER`로 분류했다.
범위 수정 내용은 지지됨, 전체 노트 내용은 UNKNOWN, 교훈 누설은 CLEAR로 나눠 기록하고 수용하지 않았다.
이 결과는 **노트 생성과 올바른 노트 학습이 다른 단계**임을 보여준다. 성공 노트를 만들기 위해 같은 답을 재생성하지 않는다.
필요한 실제 연결이 아직 없으므로 원래 순서의 11–16번을 미리 등록해 첫 16문항 블록의 검증을 이어간다.
기존 10문항 원문은 그대로 재사용하며, 성공 사례만 고른 점수로 보고하지 않는다.

새 TAT-DQA PDF의 품질 검토는 **24문항 실제 열람 후 HOLD**다. 60문항을 검토했다고 보고하지 않는다.
발견한 세 가지 명확한 실패는 다음과 같다.

- 질문에 필요한 0.6·6.6이 제공된 한 페이지 및 native layout에 없다. 원본 PDF 자체가 한 페이지이며 렌더러의 인덱스 오류가 아니다.
- 2019→2020 변화량 질문의 원래 정답은 부호가 반대이고, 표의 천 단위와 질문의 백만 단위도 맞지 않는다.
- current/non-current를 지정하지 않은 종업원 급여 질문에 원래 정답이 non-current만 택해 복수 해석이 가능하다.

별도로 native `doc.page`를 페이지 선택에 사용해 일부 원본의 마지막 페이지만 제공하던 변환 결함도 발견했다.
추가 전수 대조에서 `doc.page=1`인데 실제 PDF와 layout은 2페이지인 반례가 나와, 이 값을 정확한 페이지 수로도 신뢰할 수 없다.
원본 PDF의 실제 페이지 수와 layout을 대조해 실제 1–2페이지 전체를 제공하도록 수정·시험하되,
이것을 위 세 가지 원출처 오류의 해결로 처리하지 않는다.
기존 의견·자료·실패를 보존하고 이 출처를 선정안에서 대체한다. 수량이나 source 수를 맞추기 위한 임계값 완화는 없다.

첫 10문항의 정답 7개 중 반복/길이 검사로 2개가 제외됐고, 남은 5개 풀이 전체를 원본 이미지·native 주석과 대조했다.
GVLQA의 답만 있는 출력과 ScienceQA 지도 풀이 2개는 수용했다. 다른 3개는 정답이 맞더라도 다음 이유로 SFT에서 제외했다.

- 농도 문제는 그림의 입자 9개를 8개라고 관찰했다.
- 식물 분류는 최종 선택은 맞지만 두 선택지의 학명을 잘못 설명했다.
- 흉부 이미지 풀이에는 정상임을 확정할 수 없다는 사실에서 비정상을 결론 내리는 근거 없는 추론이 있었다.

이것은 AI 검토이며 `human_verified=false`다. 원문을 고치지 않았고, 독립 검토자가 계산한 5개 receipt SHA를
옛 동결 감사 코드로 다시 계산해 모두 일치함을 확인했다. 이 실행에 사용한 SINGLE v1의 RL 보상은 최종 답의 정오만 보기 때문에,
이런 정답/설명 오류 출력도 양의 RL 보상을 받을 수 있다. **SFT 내용 거부가 RL의 과정 정확성 인증을 뜻하지 않는다.**
실제 개선 효과와 이 보상의 한계는 별도로 검증해야 한다.

지도 노트 입력을 역추적한 결과, 기존 코드가 `INVALID_NO_FINAL`을 `NO CLEAR FINAL ANSWER`로 설명하는 것도 확인했다.
실제 원문에는 명시적인 최종 숫자가 있었고, 문제는 요구된 범위 대신 그 하한만 답했다는 점이었다.
따라서 파서의 미수용을 최종답 부재로 해석하게 할 수 있는 피드백이다. 이것이 해당 모델의 원인 분류를
유발한 정도는 분리 측정하지 않았다. 이후 SINGLE v2에서는 파서 미수용과 실제 최종답 부재를 구분하는
중립 피드백으로 바꾸고 prompt hash를 새로 고정한다. 이전 v1–v3 프롬프트·생성 원문·거부 의견은 유지한다.

후속 TATQA 고정 표본은 실제32개를 검토했고 28지지/3품질실패/1UNKNOWN으로 기록했다. 33–60번은 미검토다.
실패 하나는 필요한 원본 문단이 actor에서 빠진 경우이고, 둘은 질문하는 답이 actor의 문장에 이미 있어 이미지가 필요하지 않은 경우다.
뒤의 두 정답 라벨은 맞고 일반 과제 문맥이므로 정답 누설이라고 바꾸어 부르지 않는다.
기존 `render_ok/leak_free/gold_supported` 세 조건의 실패3개로 보고하지 않고, §7.2의 시각 적합성 조건 때문에
현재 TATQA50 공급을 HOLD한다. 원 제작자의 table-only 주석을 이용한 별도 선별 가능성을 조사하되 기존 실패는 보존한다.

기존 TATQA 변환기는 숫자만 있는 assistant 답을 수용하므로, 설명 뒤에 `Answer:`와 숫자가 붙은 계산 문항을
버리는 선택 편향도 확인했다. 새 후보는 별도 `hf-tatqa-table` 출처로 원 제작자의 train table UID와 mirror 이미지를
정확히 연결하고, `answer_from=table`, arithmetic/count, 참조 문단 없음, 최종 숫자·scale 일치를 요구한다.
풀이 설명이나 원본 문단을 모델 입력에 추가하지 않는다. 기존 후보 전체의 이미지/pixel/family와 과거 학습·held-out·
제외 family까지 대조한 뒤 새 shard를 만들며, 출처 이름만 바꿔 기존 문항을 신규로 세지 않는다.
이 조건은 계산 문항 확보 기준이고 품질 통과 증거가 아니다. 실제 표의 셀·머리글·질문·native 계산 근거 검토와
같은 고정 benchmark 전수 검사를 별도로 통과해야 선정안의 C5에 반영한다.

PDF를 뺀 새 후보 실물은 train11,483+held-out15다. 이 숫자는 최종3500이 아니다. 후보와 원래 held-out611,
과거 제외family1,820 사이의 family/image/pixel 교집합0을 확인했고, 새 전수 중복 감사의 CPU 준비를 시작했다.
이전6990 후보에 새 수동 경고 판정을 적용한 별도 계산은 신규family1,282로 여전히 목표보다898개 부족했다.
새 후보의 더 큰 합계만으로 이 부족분이 해결됐다고 처리하지 않는다.

### 12.4 이후 SINGLE v2의 코드 검증 범위

§6.2의 검토 기반 보상과 중립 파서 피드백을 구현했다. 원래 생성/검토/출처 결합에서 보상을 재계산하고,
encoding과 backward에서 다시 확인한다. 수용 boolean만 바꾸거나 A2 검토를 T1의 양의 보상 근거로 쓰지 못한다.
독립 검토는 실제16개 T1 중 양성1개인 CPU 사례에서도 분모16·원래 actions·generation 보존을 확인했다.

최종 source-bound CPU116검사(0 skip), Ruff11파일, 범위 mypy7파일이 통과했다. 별도 독립 집중12검사도 통과했다.
CPU검사는 CUDA 초기화와 optimizer step을 차단했고 시작/종료 CUDA 미초기화를 확인했다.
이전 메모리 경로 검사 중 CUDA context가 초기화된 프로세스는 종료됐으며 그 사건을 숨기거나 최종 검사와 섞지 않았다.

메모리 profile은 실제 생성·PG/full-KL·A1/A2/B·LM/FULL의 관측치를 외부 SHA와 소스/모델/GPU 조건으로 결합한다.
미측정 종류·길이·이미지 범위는 UNCALIBRATED/HOLD이며, 짧은 출력으로 미사용8192토큰 용량을 측정했다고 하지 않는다.
현재는 구현·CPU 반례 검사 범위이고, **새 v2의 실제 Qwen 실행·전체 오답노트 기울기·실측 용량 profile은 아직 미완료**다.
이미 실행한 옛 F의 결과는 이 새 버전의 성공 증거로 바꾸지 않는다.

다음 실제 시험은 기존 순서17–26번을 생성 전에 등록했다. 새 동결 소스542파일에서 기존 자료의 로컬 evidence와
승인 export를 새로 검증했고, 각각477.44초와545.06초에 완료했다. 이는 CPU 자료 검증 시간이지 모델 처리량이 아니다.
실제 실행용 계획은 출력8192토큰을 유지하고 단계 시간한도14400초·외부14430초·종료 유예30초를 고정한다.

실행 중인 첫16의 소스/한도를 변경하거나 완료된 답을 재생성하지 않는다.

새11,498후보의 OCR20,008입력은16,150개 정확한 cache 재사용+3,858개 새 계산으로 실패0에 종료했다.
이는 benchmark와 후보를 합친 엔진 입력 수다. GPU 이미지/텍스트 특징의 미계산분과 경고 판정은 아직 남아 있다.
최종3500·전체 오답 교정 기울기·실측 메모리 profile 중 하나라도 미완료이면 로컬 완료로 표시하지 않는다.

### 12.5 첫16 시간초과와 후속 실행·메모리 수정

옛 동결 SINGLE v1은 07:52:29Z에 설정된 생성 시간한도로 종료했다(exit1). T1 16개와 노트5개는 완료 원문이 남아 있고,
악보 노트1개는 STARTED, 다음 GVLQA 노트는 미생성이다. 이 블록을 완료하거나 실제 backward를 통과했다고 보고하지 않는다.
미완료 응답의 이미 생성된 token/logprob가 sampler 안에만 있다가 예외로 유실되는 것도 확인했다.
다음 버전은 실패 시 실제 부분 action·확률·입력 결합을 원장에 보존하도록 수정한다. 부분 응답을 COMPLETE/학습 행으로
승격하거나 같은 요청을 다시 생성하지 않는다. 이전 실패 원장과 동결 소스는 그대로 남긴다.

SFT 측정이 원래 가중치/분모를 우회하는 결함, 측정 실패 시 이미 끝난 증명 보고서도 저장되지 않는 결함을 수정했다.
공통 학습기의 실제 microbatch를 관측하고 원래 B×C·SFT 종류별 분모·기울기 누적을 보존한다. 증명 보고서는 측정 전에 저장하며,

독립16행/양성1개 비교가 통과했다. 실제 GPU 메모리 측정은 아직 남아 있다.

자료/소스/정책을 고정하고, 검토 WAIT와 RNG를 저장하며, 원자적으로 닫힌 checkpoint를 기준으로 cursor를 복구한다.

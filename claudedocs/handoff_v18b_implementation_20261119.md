## 운영자가 결정한 값을 전달하는 방법

1. 학습·평가 계획의 `execution_settings`에 동일한 run ID, 실제 첫 과금 UTC, 초 단위 전체·회수·평가 후 시간, 과금되는 각 포드의 시작과 스토리지 포함 시간당 단가를 적는다. `evaluation_strategy`는 `one_pod`, `two_pod`, `training_cutoff` 중 하나다. `training_cutoff_seconds`는 마지막 선택에서만 설정한다. `monitor_stop_action`은 `stop` 또는 `evaluate_checkpoint`다. `reuse_f0_raw`는 참·거짓으로 명시한다.
2. 원문 재사용을 허용한 경우 기존 F0 준비 출력과 출처 증빙 각각의 파일 경로·SHA256을 제공한다. 오래된 짧은 출력 한도의 감시 응답을 새 32K B2 감시의 기준으로 사용하면 안 된다. 준비 종료 뒤의 체크포인트가 없으면 F0 생성 재사용만으로 준비 SFT 15회까지 생략할 수 없다.
3. 학습 체인은 `python -m fine_tuning.error_note.plan plan --stage v18b-train --params … --output …`로 작성한다. 정상 BF16 계획에는 외부 백업 전송 명령을 인자 배열로 지정한다. 수신 측 `python -m fine_tuning.error_note.v18b_recovery receive --archive … --output …`의 마지막 JSON을 전달한다. `--closure-only` 응답은 묶음 내부 확인까지다. 장비를 옮겼으면 외부 자료·모델 경로까지 대조하고 재개한다.
4. 평가 전략을 사전 선택하고 동일 설정을 `v18b-eval`에 전달한다. 중단 전 체크포인트를 선택했다면 그 모델이 실제 소비한 문항 수를 보고한다. 보완 판정은 전체 900개 응답이 모인 뒤 별도로 산출한다. 두 포드 사용 시 양쪽 비용과 시작 비용을 포함한다.
5. 시간·비용 상한은 비용 지출을 제한한다. 900문항이 그 안에 끝난다는 보장은 없다. 안전한 종료를 위해 남긴 시간, 실제 포드 삭제·과금 종료 확인, 백업 수신 장비의 연결은 운영자에게 필요하다. 모델 입력·토큰 한도·평가 횟수를 줄여서 완주 처리하지 않는다.

## 독립 검토 후 반영한 네 가지

1. 8묶음째 첫 외부 감시에서 중단하면 직전 정상 체크포인트가 준비 SFT 직후일 수 있다. `evaluate_checkpoint`에서 그 실물 체크포인트·준비 트랜잭션과 판을 확인해 **준비 SFT만, 본학습 0/3,000**으로 내보낸다. 다른 사유의 0문항이나 단순 시각 예외로 이 경로에 진입할 수 없다. 최종 평가 시작에는 별도의 명시적 결정이 필요하다.
2. 교정 N에는 모델이 노트를 생성했을 때의 원 입력과 같은 문맥이 필요하다. 인코더에서 실제 프롬프트 텍스트 SHA, 토큰열, 이미지 텐서를 포함한 입력 해시를 생성 기록과 대조한다. 첫 풀이용 P0로 옮겨 학습하는 재풀이 C에는 기존 동작을 적용한다. 교정값 바이트만 N 손실에 포함된다. 인용 주변 자유 설명의 참·거짓까지 검증했다고 해석하지 않는다.
3. 로컬 수신 후 복원할 묶음에 실제 보고 파일 이름 `v18b-gate-slot-*`, `v18b-slot-*`가 들어가고, 최신 인덱스가 가리키는 파일의 해시·계획·존재까지 검사한다. 다음 슬롯의 미확정 보고를 앞 체크포인트 증거로 쓰지 않는다.
4. 그래프 OBS 통계가 실제 공급 보고 파일에 기록된다. 이미 소비된 `:OBS` 행 중 채점할 수 있는 문항에 대해 모델 정답, 항상 존재, 항상 부재의 정답 수를 같은 분모로 계산한다. 미리 생성만 된 OBS는 이 통계에서 제외된다.

전체 실험 폴더의 운영 Python 파일 280개(그중 `error_note` 65개)에 대해 구문 분석을 마쳤다. 정상 명령의 호출 경로와 자료·판·토큰의 연결을 집중 검토했고, 독립 검토에서 위 네 가지가 발견됐다. `cpu-final-3/cpu-receipt.json`의 집중 검사 153개는 실패·오류·건너뜀 0개로 끝났다. 실제 BF16 엔진의 커널·정밀도·처리 시간은 CPU 시험에서 증명할 수 없다.

## 실제 발주 전 세 선택에 관한 판단

- 학습 보상·KL은 이번 비교에서 고정하는 쪽을 권한다. 회수한 같은 149문항에서 32토큰 미만은 준비 직후 44→77개로 늘었지만, 정답은 94→96개였다. `B2_SHORT_DRIFT`에 걸린 체크포인트를 자동으로 열등하다고 단정할 수 없다. 연구 목표가 교정 학습의 효과라면 전혀 학습되지 않은 N이나 준비 직후 가중치에 900문항 비용을 쓰는 것은 근거가 약하다. `stop`은 비용을 아끼는 선택이고 `evaluate_checkpoint`는 직전 모델 자체를 측정하려는 명시적 선택이다.
- 3,000개를 전부 학습하고 14시간과 22달러를 모두 지키는 조건을 우선한다. 기존 계획의 B2 길이 시나리오는 평가 분할 시 벽시계 726분, 두 장비 합계 1,015분이다. 이 시간이 재현된다면 두 장비의 가중평균 **스토리지 포함** 단가가 약 1.30달러/시간 이하여야 22달러 안에 들어온다. 이 수치는 손익분기점이고 안전 여유가 없다. 긴 출력 가능성, 조달·수신 지연, 추가 B2 감시 213문항씩의 실제 비용을 반영한 보수적 예상이 두 상한에 함께 들어올 때만 해당 전략을 사전 선택한다. 데이터 수나 지출 한도 변경에는 별도의 선택이 필요하다.
- 준비 F0 출력 재사용을 허용하는 쪽을 권한다. 허용 대상은 출처와 해시가 맞는 외부 준비·효과 비교 응답과 그 증빙이다. 새 학습 자료는 고정 원출처에서 재구성하고, 같은 원문을 현재 학습 채점기로 다시 판정한다. 아래의 전체 CPU 확인에서 대상 640개가 일치했다. 포드에서 절약되는 순시간은 실제 전송·검증 시간을 포함해 측정해야 한다.

두 음성 대조는 정상 경로에서 노트를 요청할 오류가 없어 요청 없이 종료됐다. 잘못 수락한 교정은 0건이다. 그 결과로 임의의 틀린 노트를 이 검증기가 모두 거른다고 주장할 수 없다.

미니 캠페인은 위 두 과거 사례와 별도로 고정한 8문항을 현 정책으로 직접 풀었다. 첫 풀이 3개 정답·2개 오답·3개 잘림이었다. 공개 관측은 1개 정답·2개 오답이었고, 나머지는 단위 불일치 2개, 그래프 간선 존재 여부를 요구한 곳에 JSON 정수 `1`을 쓴 경우 2개, 기권 1개였다. **독립 검산으로 관측 오류가 확인된 2개 모두 노트를 작성했다. 노트를 작성한 총 4개 모두 스스로 `repairs=[]`를 출력했다.** 정식 캠페인 노트 4개의 교훈은 전부 재풀이에 쓸 수 있었고 실제로 4번 다시 풀었다. 3개는 정상 종료에 이르지 못했고 1개는 오답이어서 C 학습도 0이었다. 이 시험은 단계별 생성 한도가 256토큰이어서 긴 풀이 성공률이나 A100 수율을 예측할 수 없다.

따라서 이번 8개에서는 세 실패를 구분할 수 있다. 채점할 수 없게 표현한 관측, 실제로 틀렸고 수정 기회도 있었지만 모델이 수정값을 쓰지 않은 경우, 교훈을 사용한 뒤에도 재풀이가 수용 조건에 이르지 못한 경우다. 다음 관측 프롬프트는 반환할 자료형과 단위의 표기를 항목별로 명확히 하고, 노트에는 주 질문의 문장을 원 관측 질문의 `question`으로 중복 표시하지 않는 방안을 별도 검증할 수 있다. 확인된 오답에서도 빈 배열이 나왔으므로 인용 검증기의 조건만 완화해 이 사례를 학습하는 것은 불가능하다. 원문 집계·파일 해시는 `gpu-smoke-native-funnel.json`에 있다.

진단 전용 생성기가 실제 정책 판 번호를 기록하지 않아 두 양성 사례의 감사 사유에 `GENERATION_BINDING:policy_version`도 남았다. 정상 학습의 HF 생성 경로는 판 번호를 기록한다. 진단기도 같은 생성 경로를 사용하도록 고쳤고 당시의 원 응답과 감사 결과는 보존했다. 이어지는 자식 프로세스를 등록할 때 실행 기록을 덮어쓰려던 시험 감독기 오류도 수정했다. 작업자별 불변 기록과 현재 실행 기록을 분리하고, 기록 실패 때 시작한 작업자를 회수하는 동작을 CPU에서 검사했다. 이 오류가 발생한 시점까지 미니 캠페인에서 생성하거나 소비한 문항은 없었다. 같은 시험의 남은 시간에는 원래 진단·준비 원문의 해시와 최초 마감 시각을 이어받았다.

시험 감독기 수정 후 집중 CPU 검사는 155개 전부 통과했다(`cpu-release/cpu-receipt.json`, 약 57초). 별도로 v16~v18b 회귀 485개를 한 프로세스에서 실행했을 때 8개가 실패 또는 오류였다. 메모리·CUDA 초기화 상태와 검사 중에 변경된 소스·시험 설정이 포함돼 있었다. 실패한 8개는 CPU 전용 개별 프로세스에서 최종적으로 모두 통과했다. 485개 전체를 같은 조건에서 다시 함께 통과한 기록은 없다. 새 코드 등 11개 파일의 제한 범위 mypy 검사와 관련 Ruff 검사도 통과했다.

## F0 준비 파일 전송을 승인할 때의 범위

회수된 7회차 `f0-generations.json`은 20,898,793바이트이고 gzip 레벨 3에서는 1,413,350바이트다. 원본 SHA256은 `fff61c99a9e111aadd56c83175385ca9f2610b8e24c3850405c200b7aee22d17`이다. 파일에는 준비 512·효과 비교 128·옛 감시 200건이 있다. 정식 재사용 경로는 앞의 두 역할만 읽는다. 이 640개는 전부 이번 선정 문항과 ID가 일치한다. 새 감시 149+64건은 해당 단계의 B2 조건으로 새로 측정한다.

처음 세 건을 확인한 뒤 전수 CPU 검사 한 번은 145초의 진단 한도에서 종료됐다. 같은 입력·채점기로 다시 시행한 정식 `reuse-f0`가 117.85초에 정상 종료했다. **준비 512/512와 효과 비교 128/128의 요청·입력·토큰·원문이 모두 일치해 현재 채점기로 재채점됐고, 재생성이 필요한 문항은 이 두 역할에서 0개였다.** 완료 근거는 비공개 `preparation/full-reuse-release/f0-reuse.json`이다. 파일 SHA256은 `ea7ba44991c16809720d75f8573b01d9cad2841f9d71dead3e3e54f9b4b9f516`이다. 영수증의 전체 상태명 `VERIFIED_PARTIAL`은 새 감시 응답까지 재사용한다는 뜻이 되지 않도록 역할별 수치와 함께 읽는다. 로컬 검사에서 네트워크·GPU 모델 생성은 사용하지 않았다. 승인을 권하는 범위는 이 고정 원문과 출처 증빙의 비공개 전송 및 현재 채점기로의 재채점이다. 효과 비교 자료의 학습 사용권이나 게시 권한을 부여하지 않는다.

## 2026-11-19 — 운영 수정 후 저장 지점에서 재개

`restart_v18b.sh`의 기존 프로세스 일괄 종료·캠페인 이동·소스 폴더 삭제 경로를 교체했다. 다음 명령은 실행 예정인 운영 명령이다. 로컬 검증에서는 SSH를 대역으로 바꾸어 원격 Python 구문의 파싱과 인자 전달만 확인했다.

`--prepare`는 같은 검사를 수행해 새 작업 명세와 승인 기록을 만들고 `start.sh`의 dry run까지 수행한다. `--execute`는 그 뒤 새 tmux 세션을 시작한다. 원래 승인된 job의 포드 ID·소스 명세 해시를 확인하고, 기존 소유 작업·학습 잠금·엔진·GPU 작업이 남아 있으면 재개 준비를 거부한다. 원본 clone을 보존하며, 새 커밋을 fetch한 별도 clean worktree에서 고정 dependency lock을 대조한다. 실행 중 소스 수정과 프로세스 신호 전송은 없다.

새 작업은 `v18b_hotfix resume-plan`으로 만든다. 마지막 닫힌 저장 경계와 원래 학습 계약을 검증하고 `advance → require-complete → reload → export → training-artifact-seal`만 이어 간다. 첫 과금 시각·학습 순서·기존 자료·준비 풀이·준비 SFT·회수 대상은 그대로 이어 사용한다. 작업 명세·로그·내보내기는 고유 경로를 쓰므로 이전 파일을 보존한다. 최종 평가 실행기는 새 학습 산출물 봉인의 `export.root`를 읽는다. 새 실행 로그와 커밋은 `/workspace/runs/v18b/active-training-attempt.json`에 남긴다.

이 재개 경로는 허용 목록의 운영 함수 수정과 소스 주석 변경을 검증한다. 프롬프트·보상·마스크·자료·학습 설정 변경은 새 실험으로 처리한다. 따라서 최초 실패 커밋 `da57b50`을 이번에 바뀐 감시 계약으로 이어 학습하는 기능으로 해석하면 안 된다. 다음 정식 실행이 이번 계약으로 시작된 뒤 발생하는 호환 운영 수정에 쓰는 경로다. 허용한 함수 본문 내부가 실제로 운영 결함만 고치는지는 게시 전 코드 검토가 필요하다. 과거의 시간 마감 계약도 자동 변경하지 않는다.

## 2026-11-19 — 설치 뒤 자료 복원과 A100 C2를 먼저 실행하는 순서

`setup_v18b.sh`는 uv 설치와 원본 파일 사전 내려받기를 수행한다. 3,856개 기본 문항과 추가 감시 64개의 최종 복원은 학습 체인의 `prepare-data` 단계에 있다. C2는 이미 복원된 자료를 읽으므로, 아래 명령으로 같은 경로에 자료를 먼저 복원한 뒤 C2를 실행한다. 이후 정식 체인의 `prepare-data`는 기존 복원본을 검증하며 재수집·재복원을 반복하지 않는다. 설치가 출력한 `SETUP_DONE`과 `PREP_EXIT 0`을 확인한 뒤 포드 셸에서 실행한다.

```bash
set -euo pipefail
cd /root/MMDL_test
SHA='로컬 C1을 통과해 게시한 전체 40자리 커밋'
test "$(git rev-parse HEAD)" = "$SHA"
test -z "$(git status --porcelain --untracked-files=all)"
export PYTHONPATH="$PWD/src:$PWD"
export HF_HOME=/workspace/mmdl-volume/hf-cache
V="$(python3 -c 'import json; print(json.load(open("/workspace/mmdl-volume/volume_manifest.json"))["venv"])')/bin/python"
MODEL=/workspace/mmdl-volume/hf-cache/hub/models--Qwen--Qwen3-VL-4B-Instruct/snapshots/ebb281ec70b05090aa6165b016eac8ec08e71b17
DATA=/workspace/mmdl-volume/v18b-data
CACHE=/workspace/mmdl-volume/v18-cache

# 같은 원본 캐시와 같은 최종 경로를 사용한다. 이 CPU 복원 시간은 C2의 25분과 별도로 기록한다.
"$V" -B -m fine_tuning.error_note.v18b_data prepare \
  --recipe "$PWD/fine_tuning/error_note/v18_recipe.json" \
  --cache-dir "$CACHE" --output "$DATA" --tokenizer "$MODEL"

# 설치 단계가 백그라운드로 시작한 공식 7B 판정기 내려받기도 완료돼야 C2를 오프라인으로 실행할 수 있다.
grep -q '^CVDL_EXIT 0$' /workspace/cv-download.log
C2_ROOT=/workspace/runs/v18b-c2-${SHA:0:12}
test ! -e "$C2_ROOT"
mkdir "$C2_ROOT"
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 \
  "$V" -B -m fine_tuning.error_note.v18b_rehearsal run --profile a100-bf16 \
  --data-root "$DATA" --model-path "$MODEL" --output "$C2_ROOT/campaign" \
  --deadline-seconds 1500 > "$C2_ROOT/c2.log" 2>&1

# 같은 소스에서 예행 완료·외부 9개·판정기 호출 영수증을 확인한다.
"$V" -B - "$SHA" "$C2_ROOT" <<'PY'
from pathlib import Path
import sys
from fine_tuning.error_note.prep_v16b import read_sealed
from fine_tuning.error_note.single import source_manifest
sha, root = sys.argv[1], Path(sys.argv[2])
plan = read_sealed(root / 'campaign/campaign-plan.json')
receipt = read_sealed(root / 'campaign/rehearsal-receipt.json')
source = source_manifest()
assert source['base_commit'] == sha == plan['source']['base_commit']
assert source['actual_files'] == plan['source']['actual_files']
assert receipt['status'] == 'PASS' and receipt['reportable'] is False
assert receipt['profile'] == 'a100-bf16'
assert receipt['mechanical_note']['status'] == 'PASS'
assert receipt['evaluation']['external_count'] == 9 and receipt['evaluation']['judge_receipt']
print('C2_PASS', sha, receipt['wall_seconds'], root)
PY
test "$(git rev-parse HEAD)" = "$SHA"
test -z "$(git status --porcelain --untracked-files=all)"
printf 'VENV_FOR_LAUNCH %s\n' "$V"
```

이 명령은 A100의 실제 4B BF16·vLLM과 정식 캠페인 함수를 사용한다. 예행용 출력 상한·묶음 수·KV 크기는 축소된 `a100-bf16` 프로필의 값이다. 최대 길이 메모리 확인은 본실행의 기존 기능 검사에서 수행한다. C2는 감독 함수 진입부터 1,500초를 공통으로 적용한다. 각 작업자의 PyTorch 초기화·모델 로딩·생성·판정 시간을 이 기한에 포함한다. 실패·기한 초과는 해당 단계 로그에 보존하며 같은 폴더의 시험을 새 성공으로 덮어쓰지 않는다.

`C2_PASS` 후 로컬 Claude 셸에서 기존 `launch_v18b_train.sh HOST PORT POD_ID SHA FIRST_BILL HOURLY GPU_TYPE VENV_FOR_LAUNCH`를 실행한다. `SHA`는 위와 같고 `FIRST_BILL`은 포드를 만든 원래 UTC다. `VENV_FOR_LAUNCH`에는 위에서 출력한 실제 포드 Python 경로를 넣는다. C2 출력은 `/workspace/runs/v18b-c2-...`에 있으며, 정식 학습 출력 `/workspace/runs/v18b/output`과 겹치지 않는다. 정식 학습은 같은 자료 경로와 원래 F0에서 시작한다.

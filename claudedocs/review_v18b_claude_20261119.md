## 1. 결론

1. **유료 실행 보류에 동의한다.** Codex 보고서의 핵심 수치는 독립 집계와 맞았다. 노트 539건 중 수용은 0건이었고, 오류로 판정된 주장은 3,298건 중 55건이었다. 시도별 체인 시간, 재시작 원인, 소비 행 수(RL 1,280 / A1 414 / OBS 106 / C 99 / N 0)도 일치했다.
2. 보고서가 다루지 않았거나 약하게 다룬 위험이 여섯 가지 있다(§2). 그중 둘은 이번 목표에 직접 걸린다.
   - **F1 단답화.** 평가와 같은 디코딩에서 모델이 풀이 없이 답만 내는 쪽으로 무너졌는데, 이를 막는 장치가 없다. MMMU 점수에 가장 큰 위험이다.
   - **F4 시간·예산.** 이 문제를 고쳐 출력 길이가 B2 수준으로 돌아오면 평가 시간이 약 8시간이 된다. 그러면 14시간과 22달러를 단일 포드로는 동시에 지킬 수 없다.
3. 학습 전 검사와 MMMU 직전 검사는 호환 영수증 없이도 각각 약 1~2분, 약 10분으로 줄일 수 있다(F2). 실측 내역상 대부분이 안전 확인이 아니라 시간 추정용 반복 측정과 모델 재로딩이었다.
4. 로컬 RTX 5060 30분 시험은 Codex 안의 뼈대를 따르되 두 가지를 바꿔야 한다(§3). 그대로면 본학습 미니 캠페인에서 자연 교정 기회가 거의 생기지 않는다.

## 2. 추가로 확인한 문제

### F1. 평가 디코딩에서의 단답화를 아무 장치도 막지 않는다 — 치명

| 7회차 외부 감시 200문항 (평가와 같은 B2 샘플링) | 길이 중앙값 | 32토큰 미만 | 짧은 응답 예 |
|---|---:|---:|---|
| 준비 SFT 직후 (`monitor-post-prep`) | 156.5 | 49 | — |
| 전역 갱신 34, 본학습 19묶음 뒤 (`monitor-signal-gate`) | **7.5** | **120** | `A. Yes`, `B. No`, `C. none of the listed weed species` |

같은 시점에 학습 흐름의 첫 풀이는 중앙값 230~260토큰, 16개 중 짧은 응답 1~6개였다. 두 숫자가 크게 갈린 이유는 샘플링 설정이 다르기 때문이다.

- 학습 T1은 `TRAIN_SAMPLING_V16B`(top-p 1.0, top-k 0)로 생성된다 (`campaign_v16b.py:800`).
- 외부 감시와 MMMU는 `EVAL_SAMPLING_V16B`(top-p 0.8, top-k 20)를 쓴다 (`prep_v16b.py:316`, `protocol.py:579-580`).
- 학습 흐름 감시 `COLLAPSE_SHORT`(16개 중 12개 이상, 두 묶음 연속)와 `COLLAPSE_LEN`은 학습 흐름만 본다 (`guard_v16b.py:68-86`). 게다가 v18에서 `COLLAPSE_LEN`은 경고로만 바뀌었다(`f360427`).
- 결국 평가 디코딩에서는 이미 답만 내는데, 감시 장치는 원리상 이를 볼 수 없었다.

원인 가설(미검증):
- 정답 첫 풀이에는 전 토큰에 양의 PG가 걸린다(b=0, `train_v17.py:535-537`).
- 오답에는 현재 확률 0.5 이하 토큰에만 음의 PG가 걸린다(`rl.py:147-152`, `train_v17.py:521-523`). 7회차에서 남은 음의 토큰은 15.7%였다.
- KL 기준점도 학습 샘플러 출력 위에서 계산된다.
- 그 결과, 쉬운 객관식 문항에서 답부터 쓰는 시작 토큰이 잘린 분포의 최빈값으로 올라섰을 가능성이 있다.

과거 결과도 같은 방향이다. v4는 단답 비율이 28%에서 44%로 늘었고 MMMU가 522였다. v17은 B2 정상 종료 문항에서 순 −22였다. **v18b가 오답노트 경로만 고치고 이 문제를 그대로 두면 MMMU는 B2보다 낮아질 위험이 크다.**

필요한 보강:
- (a) 외부 감시를 본학습 8·16묶음째에 먼저 돌린다. 그 결과로 **평가 디코딩 기준 단답 비율**을 F0·준비 직후와 같은 문항끼리 짝지어 비교하는 감시를 추가한다.
- (b) 그 감시가 발동했을 때의 처리를 실행 전에 정한다. 예: 마지막 정상 저장 경계를 최종 체크포인트로 고정한다(사전등록 규칙이라 사후 선택이 아니다).
- (c) 원인을 고치는 보상·KL 변경안(예: 객관식에서 32토큰 미만 정답에 양의 PG 제외, 첫 64위치 KL을 평가 샘플러 기준으로 측정)을 Codex가 제안한다. 학습 방식 변경이므로 사용자가 승인한다.

### F2. 학습 전 14분, MMMU 직전 59분은 대부분 안전 확인이 아니다

7회차 `calibration/` 영수증의 실측 내역:

| 학습 전 BF16 검사 14.1분 | 시간 | 성격 |
|---|---:|---|
| 최대 형상(8192 행동 토큰) 순전파·역전파 | 약 17초 | **메모리 안전 확인 (필요)** |
| HF·vLLM 동시 상주 확인 | 3.6초 | **필요** |
| A/B/C 갱신 비용 측정 (예열 + 3회씩) | 약 8.2분 | 시간 추정용 |
| 나머지(별도 프로세스의 모델·엔진 로딩 등) | 약 5.5분 | 다음 단계에서 다시 로딩 |

- 메모리 안전 확인 21초만 `campaign-advance`가 모델을 띄운 직후 같은 프로세스에서 한 번 수행하면 된다.
- A/B/C 측정은 첫 본학습 묶음들의 실측 시간으로 대신한다.
- 이렇게 하면 **호환 영수증이 없는 새 포드에서도 약 1~2분**이다. Codex 보고서의 "냉간 14~16분" 분기가 필요 없어진다.

MMMU 직전 검사(v17 58분 51초)도 같은 구조다.

| 항목 | 시간 | 판단 |
|---|---:|---|
| 9칸 × 32,768토큰 강제 생성 | 31.24분 | 동시 9칸 안전은 계산으로 보장된다. 9 × 40,960 = 368,640 ≤ 0.9 × 444,416 = 399,974이고, vLLM은 KV를 미리 할당한다. 엔진 시작 때 KV 용량을 읽는 확인으로 대체한다. |

→ 새 플랫폼에서도 약 10분이다. 장문 강제 생성을 없애도 정확성은 잃지 않는다. 잃는 것은 사전 시간 추정뿐이다. 진행 중 선점 증가는 Codex §7-4의 계측으로 잡는다.

### F3. 포드 장애가 나면 학습 전체를 잃는다

- v18 포드는 커뮤니티 클라우드, `/workspace`에 200GB 포드 볼륨을 붙여 만들었다(`pod-scripts/create_gql_v18.py:34-36`).
- 학습 감시 스크립트에는 실행 중 포드 밖으로 복사하는 단계가 없다(`monitor_v18_train.sh`에 scp/rsync 없음). 회수는 끝에서 한 번만 했다.
- 호스트 장애나 강제 삭제가 나면 그때까지의 학습 비용이 모두 사라진다. 11-01 EU-SE-1 저장소 정지 때 300문항 체크포인트를 실제로 잃은 전례가 있다.
- 보강: 저장 경계(약 16슬롯, 30분)마다 Codex §15.1의 "완결 경계 묶음"(7회차 실측 약 1.7GB)을 로컬로 복사하고 해시를 대조한다. 최근 2벌을 보관한다. 읽기 전용 복사라 GPU를 멈추지 않는다.
- 이 장치가 있으면 장애 비용을 "최대 30분 학습 + 새 포드 설치"로 제한할 수 있다.

  - ③ 상한을 약 25달러로 조정
- Codex 보고서는 3,000문항 자동 축소를 금지한다. 그러니 이 규칙은 **사전등록된 마감 규칙**으로만 둘 수 있다.

### F5. 그래프 관측 질문은 시각이 아니라 사전확률을 학습시킬 수 있다

- 그래프 OBS 질문은 항상 "번호가 가장 작은 두 노드 사이의 간선"이다. 적격 223개 중 127개(57%)가 "없음"이다.
- 7회차에서 Qwen은 84개 중 34개를 맞혔다. 늘 "없음"이라고만 답해도 56개를 맞힌다(Codex §12.2).
- OBS 오류 54개 중 50개가 이진값이다. 그래서 OBS RL은 그림을 보지 않고 "없음"이라는 사전확률을 배우는 쪽으로 갈 수 있다.
- N 수정도 대부분 `true→false` 한 토큰이 된다.
- 보강: 문항별 해시 seed로 "실제 간선인 쌍 / 간선이 아닌 쌍"을 반반 골라 질문한다. OBS 정답률은 늘 같은 답을 내는 기준선과 함께 보고한다.
- 규모 현실성: 적격 비율이 7회차와 같다면 3,000문항 전체의 실제 관측 오류 기회는 약 115개다. 전부 교정에 성공해도 N 감독 토큰은 수백 개 수준이다. 7회차 RL은 373,486토큰이었다.
- **v18b의 N은 "자기 교정이 실제 학습에 들어간다"는 작동 증명이다. MMMU 점수를 움직일 주된 경로는 RL·A1·C다.** 결과 보고에서도 이렇게 구분해야 한다.

### F6. 사람의 결정을 기다리는 지점이 14시간을 깎는다

- v17 평가는 PF5 시각 판정 예외 승인을 사용자에게 받고서야 진행됐다.
- v18은 N=0을 발견하고 사용자가 정지를 결정할 때까지 슬롯이 계속 소비됐다.
- 밤 시간에 이런 대기가 생기면 여유 17분은 바로 사라진다.
- 실행 전에 아래 처리를 모두 문서로 정한다.

| 실행 중 생길 수 있는 일 | 사전등록할 처리 |
|---|---|
| PF5 시각 판정의 검정력 부족 | v17처럼 예외로 기록하고 진행. 실패와 구분해 보고 |

| KV 선점 증가 | 처리 방법 |
| 예산 경계 | 처리 방법 |
| 코드 결함 | 저장 경계에서 정지하고 준비 체크포인트부터 재사용 재시작, 또는 종료 |

### 참고: 확인 결과 문제 없던 항목

- v17의 평가 manifest 경쟁은 현재 `v17_eval.py:414-421`의 `fcntl` 잠금으로 해결돼 있다.

## 3. RTX 5060 30분 시험 — Codex 안에 대한 보강

Codex §16의 0~30분 시간표를 그대로 쓰되 다음을 바꾼다.

1. **CPU 회귀는 30분 밖에서 먼저 한다.** 무료이고 시간 제한도 없다. 회귀에는 다음이 포함돼야 한다.
   - v18 실패 5종의 재현 시험: 용량 영수증 버전, None 키 봉인, 미채점 OBS 마스크, 꼬리 손상 재개, 회수본 누락 참조
   - 6·7차 감시 이력 재생
   - 둘째 묶음 진입까지 가는 CPU 미니 캠페인
   - 30분은 GPU 단계만 잰다.
2. **미니 캠페인 8문항은 OBS 적격 그래프·장면 문항에서 사전 규칙으로 고른다.** 봉인 순서대로 고르면 적격 비율이 8.7%(261/3,000)라 기대 적격 문항은 0.7개다. 그러면 자연 N 경로는 거의 확실히 "기회 없음"으로 끝난다. 진단용 4문항은 제외하고, 결과를 보기 전에 규칙(예: 봉인 순서상 첫 GVLQA 6개 + CLEVR 2개)을 정한다. 결과는 "기능 시험"으로만 표기하고 본학습 수율로 쓰지 않는다.
3. **새 PID 재로딩을 강제 종료 후 재개로 바꾼다.** 둘째 묶음 저장 직후 셋째 묶음 생성 중에 프로세스를 SIGKILL한다. 그다음 정상 진입점으로 재개해 다음 슬롯을 1회 소비한다. 재로딩과 재개, 중복 소비 0을 한 번에 확인할 수 있다. Codex가 찾은 "가중치는 있는데 재개 실패" 경로를 실제 GPU 프로세스로 덮는다.

| 누적 | 실행 | 합격 기준 |
|---|---|---|
| 0~3분 | 오프라인 환경, NF4 캐시 해시, 이미지 4장 해시, VRAM·디스크 확인 | 전부 일치 |
| 3~10분 | 진단 NOTE 4건: 실제 오류 2(GVLQA 005290, CLEVR 003539), 음성 2(GVLQA 005255, Geometry 004545) | 음성 거짓 수용 0. 양성은 결과 그대로 기록 |
| 10~22분 | F0에서 준비 1슬롯 + OBS 적격 8문항 × 4묶음 + 지연 정산 3슬롯. 둘째 묶음 저장 뒤 SIGKILL | 행 소비·마스크·지연 N/C 정산 |
| 22~27분 | 새 PID로 정상 재개, 다음 1슬롯 소비, 마지막 경계 대조 | 커서·optimizer·RNG 일치, 중복 소비 0 |
| 27~30분 | 부모별 집계와 보고 | 각 항목을 PASS / NO_OPPORTUNITY / FAIL로 따로 표기 |

**유료 진행 조건(전부 충족):**
- (1) CPU 회귀가 모두 통과한다.
- (2) 실제 Qwen이 쓴 N이 1건 이상이다. 진단 또는 미니 캠페인에서 나오면 되며, 그 토큰이 기울기 → optimizer → 저장 → 재개까지 연결돼야 한다.
- (3) 음성 대조의 거짓 수용이 0이다.
- (4) 강제 종료 후 재개가 통과한다.
- (5) F1 감시가 구현돼 있다.

(2)가 0이면 유료 실행에 들어가지 않는다. 오답노트가 작동하지 않는 상태로 돈을 쓰는 것이 v18과 같은 실패이기 때문이다.

## 4. 런포드 진행 권장 순서

| 단계 | 내용 | 진행 조건 |
|---|---|---|
| 0. 무료 | Codex가 P0 수정, F1·F2·F3 보강, 마감 전달(Codex §15.3)을 구현. CPU 회귀와 회수본 재생 | 전부 통과 |
| 1. 로컬 30분 | §3 시험 | 유료 진행 조건 5개 |
| 2. 결정 | 사용자가 F4 우선순위(①/②/③), F0 원문 업로드 허용, F6 사전등록 처리를 확정. 실제 잔액 ≥ 사용 상한 + 회수 예약금 1.5달러(22달러면 23.5달러) | 문서로 고정 |
| 3. 포드 발주 | 커뮤니티 A100 80GB SXM·PCIe 중 가장 싼 것. 시간당 가격 표시. 첫 과금 시각을 모든 단계의 시계로 전달 | — |
| 4. 설치 | uv·모델·원출처·Compass 7B 다운로드를 병렬로 하고 종료 코드와 파일 전체를 확인. 학습 전 확인은 F2대로 같은 프로세스에서 1~2분 | 실패 시 즉시 원인 기록 |
| 5. 본학습 | 첫 묶음부터 학습 진도로 인정. 8·16묶음째 외부 감시(F1), 16슬롯마다 경계 묶음 로컬 복사(F3), 슬롯별 ETA 갱신. 첫 실제 N 포함 슬롯의 시간·메모리 기록 | 사전등록 처리만 수행 |
| 6. 평가 | 최종 1모델 비병합 재로딩, 평가 전 확인 약 10분(F2). 생성 토큰/초가 B2 수준이면 F4 결정에 따라 둘째 포드 분할 | 900개·문항당 답 1개·V8 확정 |
| 7. 회수·정리 | 평가 중에도 닫힌 shard를 점진 회수. REMOTE→LOCAL 검증 뒤 포드 삭제·잔존 자원 0 확인. 정지 API 실패는 재조회(Codex §14) | — |

v18 실패 1~7이 이 순서에서 어디서 잡히는지:

| v18 실패 | 잡히는 단계 |
|---|---|
| 1 OCR 라이브러리 | 4단계 설치 검사 (실제 binary 호출) |
| 2·4·5 연결 버그 | 0단계 CPU 회귀 |
| 3 PF5 | 4단계 같은 프로세스 확인 + 사전등록 예외 |
| 6 길이 감시 | 0단계 감시 이력 재생 + F1 감시 |
| 7 N=0 | 1단계 유료 진행 조건 (2) |

이 중 유료 장비에서만 처음 볼 수 있는 것은 BF16·vLLM 관련 항목뿐이다. 그 항목이 실패해도 F2 덕분에 재시작 비용은 수분이다. 단, Codex §6.2의 단계별 재사용(준비 원문·준비 체크포인트)이 구현돼 있어야 한다.

## 5. 아직 증거가 없는 것

다음은 모두 미검증이다. 문서와 계획은 실행 증거가 아니다.
- v18b의 자연 N 수율
- 단답화를 고친 뒤의 MMMU 효과
- A100 실제 처리량과 출력 길이
- 14시간·22달러 완주

## 1. 결론: 학습은 실행됐지만, 틀린 문제를 독립적으로 해결하는 감독 신호가 부족하다

## 2. 결과부터 정확히 읽기

### 2.1 이 900문항은 MMMU `validation`이다

사용자가 말한 “900문제 테스트”는 프로젝트에서 고정한 **MMMU validation 30과목 × 30문항**이다. MMMU test나 MMMU-Pro 결과가 아니다.

| 모델 | 예전 오답 342: 정답 수 | 예전 정답 558: 정답 수 | 합계 | 정확도 | 전체 출력 중앙값 |
|---|---:|---:|---:|---:|---:|
| 미학습 F0, 현재 8K 조건 | 57 | 484 | 541 | 60.11% | 444토큰 |
| 300문항 노트 모델, seed 3407 | 79 | 미평가 | 알 수 없음 | 알 수 없음 | 900문항 값 없음 |
| 1판 3,417문항 | 64 | 473 | 537 | 59.67% | 299.5토큰 |
| 버전 2 | 58 | 486 | 544 | 60.44% | 464.5토큰 |
| 기존 제출 B2, 32K 조건 | 0 | 558 | 558 | 62.00% | 449토큰 |

B2의 342/558 구분은 B2 자신의 정오로 정의했으므로 마지막 행의 0/558은 정의상 값이다. 다른 실행의 같은 군 성능과 혼동하지 않는다.

현재 v2에서 **62.00%를 초과하려면 최소 559개**, **67.4%를 수치상 초과하려면 최소 607개**가 필요하다. 각각 지금보다 순증 15개, 63개다. 67.4는 공식 비교값이지 이 환경에서 측정한 미학습 점수가 아니다. 607/900을 달성하더라도 공식 결과와 평가 조건이 다르면 동일한 평가법에서 우위가 입증됐다고 말할 수 없다.

### 2.2 전체 900문항 짝 비교

저장된 `predictions.jsonl`을 ID로 결합했다. F0·v1·v2 모두 같은 900개이며 wrong342/rest558 사이 중복·누락이 없다. 저장된 정오를 그대로 사용했고 새 파서로 점수를 바꾸지 않았다.

| 이전 → 이후 | 새로 정답 | 새로 오답 | 순변화 | 양측 exact McNemar p |
|---|---:|---:|---:|---:|
| F0 → v2 | 65 | 62 | +3 / +0.33%p | 0.8592 |
| F0 → v1 | 70 | 74 | −4 / −0.44%p | 0.8027 |
| v1 → v2 | 81 | 74 | +7 / +0.78%p | 0.6300 |

F0/v2는 둘 다 정답 479, 둘 다 오답 294다. 문항별 짝 bootstrap 10,000회, 난수 seed 3407의 차이 95% 구간은 **−2.11~+2.78%p**다. 이것은 저장된 한 쌍의 실행에서 문항을 재표집한 구간이며, 학습 재실행·전체 900문항의 seed 변동을 측정한 구간이 아니다. 문항 간 독립성 가정에도 한계가 있다.

이전 보고에서 바로잡을 표현은 다음과 같다.

- `p=0.86`은 “우연일 확률 86%”가 아니다. 정오가 바뀐 문항의 두 방향이 동등하다는 귀무가설 아래 관측한 차이 이상이 나올 확률이다. **개선 근거가 부족하다는 결론이지 두 모델이 동일하다는 증명은 아니다.**
- `sqrt(0.62×0.38/900) ≈ 1.6%p`는 문항을 이항 표본으로 보는 표준오차다. 같은 900문항을 다른 seed로 다시 풀었을 때의 실행 변동을 직접 잰 값이 아니다.
- 300 모델의 `56.33 → 70.00`은 **342개 중 평균 정답 개수**다. 정확도는 16.47% → 20.47%, 차이는 **+4.00%p**다. +13.67%p가 아니다.
- 3,417 모델의 평균 63.00개는 56.33개보다 +6.67개, 즉 이 342개 안에서 +1.95%p다.

### 2.3 300문항 모델의 이득도 노트 자체 효과로 확정할 수 없다

| seed | F0 정답 | 300 노트 정답 | 획득 / 손실 | exact p |
|---|---:|---:|---:|---:|
| 3407 | 57 | 79 | 49 / 27 | 0.0154 |
| 3408 | 63 | 67 | 39 / 35 | 0.7275 |
| 3409 | 49 | 64 | 34 / 19 | 0.0534 |

세 seed에서 방향이 같고 사전 확대 문턱은 통과했다. 하지만 같은 342문항을 반복한 결과를 서로 독립인 1,026문항으로 합쳐 검정하면 안 된다. 이 부분집합 자체도 과거 오답으로 선택돼 있다.

더 직접적인 노트 대조는 seed 3407의 **풀이만 학습 69개 대 노트 포함 79개**다. 획득 29·손실 19, p=0.1934다. 노트 자체가 이득을 만들었다는 증거는 아직 부족하다. 두 모델 모두 length 종료 71개라서 이 +10개를 단순한 잘림 감소로 설명할 수도 없다. 300 모델의 558문항 미평가를 메우는 것은 진단 가치가 있지만, 좋은 과거 모델을 골라 제출하는 근거로 사용하면 안 된다.

**대조군에도 중요한 혼란 요인이 있다.** [contract.py:216](/mnt/c/projects/multimodel/fine_tuning/error_note/contract.py:216)의 `select_rows(arm='solution')`는 B를 빼는 동시에 **모든 A의 경로를 LM으로 바꿔 Vision 학습을 끈다.** 행 수가 줄면서 A의 정규화 계수도 바뀐다. 따라서 이 비교는 순수한 노트 제거 실험이 아니라 노트·학습 경로·상대 가중치가 함께 다른 파이프라인 비교다.

## 4. 실제 목적함수: 무엇을 얼마나 가르쳤는가

### 4.1 파이프라인과 학습·평가 입력

```text
이미지 + P0 ──정답 없이 1회──> T1 ──학습용 채점──> 정오
                                │
이미지 + P0 + T1 + 정오 + gold ──> 노트 B
                                │
                 오답이면 Lesson 누설 검사
                                │
이미지 + Lesson + P0 ──1회──> 재풀이 ──정답·품질 필터──> A2

학습 A1/A2 입력: 이미지 + P0                  목표: 채택한 풀이
학습 B 입력:    이미지 + P0 + T1 + 정오 + gold  목표: 노트
MMMU 평가:     이미지 + P0                    답: 한 번 생성한 출력 하나
```

노트 입력에 정답을 주는 것은 현재 허용된 설계다. 이것 자체가 벤치마크 오염이나 구현 오류는 아니다. 그러나 **정답을 받은 뒤 해설하는 능력과 정답 없이 처음 푸는 능력은 다른 조건부 작업**이다. 전이는 가능하지만 자동으로 성립하지 않는다. 입력의 오답 토큰을 손실에서 마스킹해도 모델은 그 문맥과 정답을 보고 B를 예측한다.

### 4.2 행의 수와 손실 계수

실제 코드의 각 갱신 손실은 다음 형태다.

`L_g = (1 / 갱신의 행 수) × Σ행 [해당 응답 토큰들의 평균 음의 로그확률]`

따라서 토큰 1,000개의 풀이 한 행이 토큰 100개의 노트 한 행보다 자동으로 10배 큰 가중치를 갖지 않는다. 학습은 토큰 전체의 단순 평균이 아니라 **행 안에서 평균한 뒤 행들을 평균**한다.

| 목표 | 행 수 | 전체 행 비율 | 214개 갱신의 실제 행 계수를 평균한 비율 |
|---|---:|---:|---:|
| B: 정답을 받고 쓴 노트 | 3,365 | 68.17% | **68.53%** |
| A1: 이미 맞힌 첫 풀이 | 1,460 | 29.58% | **29.25%** |
| A2: 필터가 채택한 재풀이 | 111 | 2.25% | **2.22%** |

풀이 A의 **92.93%가 이미 맞힌 T1**이다. 실제 LR로 가중한 계수도 69.07% / 28.69% / 2.24%로 비슷하다. 단, 이 비율은 목적함수 계수의 설명이다. **“모델이 배운 것의 69%가 노트”, “기울기의 69%가 노트”라고 말할 수 없다.** 응답별 기울기 크기·방향, Adam 상태, 경로 및 clipping이 다르다.

| T1 저장 판정 | 문항 수 | T1 풀이 A | 재풀이 A | 노트 B | 노트만 학습 | 아무 행도 없음 |
|---|---:|---:|---:|---:|---:|---:|

| 길이 한도 | 283 | 0 | 14 | 278 | 264 | 5 |
| 전체 | 3,417 | 1,460 | 111 | 3,365 | 1,798 | 48 |

T1 실패 1,367개 중 **1,210개는 노트만**, 111개는 노트와 재풀이, 46개는 둘 다 없다. 111개도 아래 누설 감사에 따라 “완전히 정답 비노출로 해결한 문항 수”로 인증할 수 없다.

**[추정]** 이 구조는 정답률을 올릴 새로운 풀이 경로를 충분히 공급하기보다, 자신이 이미 성공하는 행동과 정답을 본 뒤의 설명 문체를 강화하기 쉽다. 추가 노트 수를 늘리는 것만으로 부족한 해결 경로가 생길 이유는 약하다.

### 4.4 Vision 경로도 실제로는 노트 위주다

FULL 720행은 B 647 + 재풀이 73이다. T1 FULL은 0이다. 자기 신고 MISREAD가 있는 정답 T1을 제외하는 규칙의 결과다. FULL 경로 내 행 계수의 약 90.17%가 노트에 해당한다.

**[추정]** 작은 편향된 자료로 시각-언어 연결부를 바꾸는 것이 기존 능력 보존에 영향을 줄 수 있다. 그러나 현재 로그만으로 Merger나 Vision이 하락의 원인이라고 지목할 수 없다. 노트의 MISREAD도 실제 시각 오류의 독립 인증이 아니다. 경로 기준 변경·Merger/Vision 동결 비교는 현재 사용자 결정과 다른 별도 실험 제안이다.

## 5. 학습용 채점과 응답 형식의 충돌

### 5.1 “V8로 채점”이라는 설명에 숨은 두 단계

Geometry 집계는 **숫자 표기의 동일성 감사**다. 모든 풀이의 의미를 검증해 새 점수를 부여한 것이 아니다. 다만 `60^\circ`, `\boxed{7}`, `x = 130°`, 단위가 붙은 수치가 bare number 정답과 불일치 처리된 구조는 확인된다. 추출된 값이 문장 전체인 경우도 short_text exact 비교에서 실패한다. short_text 274문항의 alias 사전은 전부 비어 있다.

### 5.2 잘못된 실패 피드백은 노트까지 바꾼다

이 78개 MapQA의 노트는 모두 `Cause: NONE`이고 B로 채택됐다. 모델 입장에서는 자신이 정답을 썼는데 “명확한 최종답 없음”이라는 피드백을 받았다. 이때 오류를 인정하지 않는 노트를 모두 “모델이 고집을 부렸다”고 분류하면 분석이 잘못된다.

반대로 다른 사례에서는 모델이 실제로 틀렸는데도 기존 주장을 유지한다. **채점 오류에 대한 타당한 반박과 잘못된 자기합리화를 먼저 분리해야 한다.**

### 5.3 최소 32토큰은 별개의 병목이다

78개 MapQA 정답은 모두 6~16토큰, 중앙값 11토큰이다. 향후 채점기를 올바르게 만들어도 이 행들은 현재 최소 32토큰 규칙에 걸린다. 수정 하나로 78개 풀이가 곧바로 학습된다고 계산하면 안 된다.

기존에 정답으로 판정된 T1 2,050개 중 A에서 제외된 590개의 사유는 다음과 같다.

| 사유 | 수 |
|---|---:|
| 32토큰 미만 | 375 |
| 반복 | 182 |
| 4,096토큰 초과 | 14 |
| 노트가 T1의 시각 오독을 자기 신고 | 19 |

짧은 정답 제외 375개에는 ScienceQA 118, GVLQA 88, MapQA 82, SLAKE 78, PlantVillage 9가 있다. SLAKE는 정답 T1 88개 중 78개를 길이로 제외해 첫 풀이 A가 10개만 남았다.

**[제안]** 짧은 답이 정당한 문제와 설명·계산이 필요한 문제의 계약을 구분한다. 32토큰 기준을 일괄 없애는 것도, 답에 군더더기를 붙여 통과시키는 것도 해법으로 확정하지 않는다. 해당 자료를 단답형 보조 과제로 소량 유지할지, 목표와 맞는 다단계 문제로 교체할지를 먼저 정한다. 1판의 짧은 출력 문제를 고려해야 한다.

**수정 원칙:** 학습용 typed 채점만 새 버전으로 고치고, 기존 원문·점수는 보존한다. 잘못된 피드백으로 생성한 노트는 라벨만 몰래 바꿔 재사용하지 않는다. 새 protocol에서 올바른 피드백으로 생성·검증할 대상을 따로 정한다. **공식 MMMU V8를 완화해 점수를 올리자는 제안이 아니다.**

## 6. 정답 비노출 재풀이에 실제 누설이 있었다

`hint_leak()`는 보기 기호·정답 문구·일부 답 표현을 검사한다. 하지만 전체 보기 문자열을 검사하는 것만으로 약어·동의어·정답을 유일하게 가리키는 표현을 잡을 수 없다. [contract.py:334](/mnt/c/projects/multimodel/fine_tuning/error_note/contract.py:334)

직접 대조한 사례:

- ID: `hf-plantvillage:plant_photo:train:000800:8081bf12f7acbc32`
- 정답 보기의 이름은 `Tomato Yellow Leaf Curl Virus`다.
- 노트 Lesson은 해당 병의 약어 **TYLCV**를 사용하며 다른 후보 **TMV**와 대조한다.
- 저장값은 `hint_leak: null`이다.

**[확인]** 적어도 한 개의 채택 재풀이가 정답 보기의 의미를 교훈으로 받았다. 이것은 MMMU 오염이 아니라 **학습 과정 안에서 “정답 없는 교훈” 계약을 지키지 못한 사례**다. 유병률·전체 점수 영향은 확인하지 못했다. 따라서 111은 “기존 필터가 채택한 재풀이”라는 상한이며, 그 모두를 누설 없는 새 해결로 세면 안 된다.

**[제안]** 다음 실행 전 채택 111개의 교훈·보기·재풀이 연결을 전수 감사한다. 출처의 공식 alias·약어와 문항별 의미 누설을 구분해 기록한다. 검사에 실패한 응답을 사람이 고쳐 학습 행으로 바꾸지 않는다. 새로 채택할 문항도 누설 불확실 상태를 통과로 취급하지 않는다. 노트 B에서 gold를 사용하는 것과 A2 생성에서 gold를 숨기는 것은 별도 계약으로 관리한다.

## 7. 노트는 학습됐지만, 올바른 오답노트를 학습했다는 인증은 없다

### 7.3 교훈의 문체와 전이 가능성

수용 B의 Lesson은 모두 서로 다른 문자열이지만 중앙값 37단어다. 2,720개가 `Always`로 시작하고 2,428개에 `verify`가 있다. 이는 반복되는 검토 문체의 증거일 뿐, 그만큼 무의미하거나 유의미하다는 의미 점수는 아니다.

좋은 교훈은 다음 문제에서 실행할 수 있는 관측·계산·확인 절차를 담아야 한다. 현재는 “정확히 확인하라”는 일반 지시와 실제로 틀린 사실이 함께 학습될 수 있다. 제목을 다 채웠는지와 **어느 잘못된 행동이 어떤 올바른 행동으로 바뀌었는지**는 다른 측정이다.

**[제안]** 노트 평가를 형식 통과, 관측 정확성, 오류 위치의 타당성, 교훈의 정답 비노출, 후속 P0 성능으로 분리한다. 전체 자연어를 프로그램이 검증할 수 없으면 검증 가능한 출처 사실과 나머지 미확정 부분을 구분한다. 미확정 내용을 자동으로 참으로 취급하지 않으며, 상위 모델 해설을 대신 작성해 학습시키지 않는다. AI 분석은 계속 `human_verified=false`다.

## 8. 문제가 너무 쉬운가, 형태가 다른가: 둘 다 있고 어려운 문제도 잘못 구성돼 있다

### 8.1 출처별 실제 감독량

다음 정답률은 **현재 학습용 채점의 저장값**이며 앞서 발견한 형식 오류를 보정하지 않았다.

| 출처 | 문항 | T1 정답 | 기록 정답률 | T1 중앙 토큰 | A: 첫 풀이 / 재풀이 | B |

| ScienceQA | 936 | 878 | 93.8% | 138 | 749 / 14 | 932 |
| ChEBI role | 400 | 129 | 32.3% | 1,366.5 | 89 / 13 | 395 |
| SSMR | 393 | 160 | 40.7% | 2,150 | 84 / 10 | 377 |
| Geometry3K | 380 | 155 | 40.8% | 582 | 120 / 15 | 371 |
| GVLQA | 364 | 284 | 78.0% | 288.5 | 151 / 6 | 356 |
| MapQA | 280 | 110 | 39.3% | 11 | 23 / 4 | 277 |
| DeepWeeds | 199 | 76 | 38.2% | 261 | 74 / 33 | 199 |

ScienceQA는 전체 문항의 27.4%지만 **풀이 A의 48.6%, 첫 풀이 A의 51.3%**다. 쉬운 문제의 감독이 필터를 통과하면서 상대적으로 더 커진다. 반대로 답을 잘 못 만드는 출처는 노트만 많이 남는다.

### 8.2 숫자로 센 분야 수가 실제 전공 범위와 다르다

- **Sociology 152개는 모두 MapQA다.** [hf_cauldron.py:78](/mnt/c/projects/multimodel/fine_tuning/notebook_rl/adapters/hf_cauldron.py:78)는 문제 내용이 아니라 hash의 홀짝으로 Sociology/Geography를 정한다. 사회학 지식 학습 근거로 보고하면 안 된다.
- History 200개는 ScienceQA이고, 그중 **180개가 식민지 이름을 묻는 같은 유형**이다. T1은 194/200 정답, 중앙값 69토큰이다. 대학 역사 추론과 동일하지 않다.
- ChEBI role 400개는 하나의 분자 역할 질문 틀, 음악은 질문 문자열 5종, NCT-CRC와 DeepWeeds는 각각 질문 문자열 하나다. 이미지가 다르므로 중복 문항이라고 단정하지 않지만 **문항 수가 작업 다양성을 과장**한다.
- DeepWeeds는 **105/199의 gold가 “목록의 종이 아님”**이다. 이 분포에서의 분류 능력은 대학 농학·복합 추론과 다르다.
- 실제 대학 수준 회계·경영·공학 등의 다단계 문제는 부족하다. 기존 14과목 라벨을 그 분야 전체 학습으로 해석할 수 없다.

MMMU 자체는 대학 시험·교재 등에서 모은 전문 지식과 여러 형태의 시각 추론을 요구한다. 같은 분야 이름이라도 객체·병명 분류와 규칙 적용·계산·자료 통합은 다른 작업이다. [MMMU 원 논문](https://arxiv.org/html/2311.16502v4)

### 8.3 어려운 문제를 더 넣기만 해도 안 된다

GVLQA의 364개 중 342개는 Yes/No이며, 나머지 **22개 max-flow는 T1 정답 0, 재풀이 정답 0, 풀이 A 0, 노트 B 18**이다. 여기서는 어려운 계산 문제를 넣었지만 검증된 해결 절차를 배우는 데이터는 생기지 않았다.

ChEBI의 역할은 분자 외형만 보고 일반 규칙으로 쉽게 유도할 수 있는 값이 아니다. 정확한 분자 식별과 약학 지식을 요구할 수 있다. 오답률이 높다는 이유만으로 좋은 추론 훈련 과제라고 볼 수 없다.

**[추정]** 현재 풀에는 너무 쉬운 반복 유형, 실제로 어려우나 정답 풀이를 얻지 못하는 유형, 정답 형식 때문에 실패로 보이는 유형이 섞여 있다. 단일 “정답률 60%”나 8K 도달률로 난도를 선택하면 세 가지를 구별하지 못한다.

**[제안]** 문항 수·과목 이름 대신 `출처 × 실제 작업 × 이미지 의존성 × 답 형태 × 원본 난도 × 검증 가능 단계`로 분포를 기록한다. 기존 데이터의 grade/difficulty와 서로 다른 문항의 단일 시도 결과를 활용한다. 난도 측정을 명분으로 문항당 여러 답을 생성·선택하는 방식은 현재 규칙에서 자동 허용되지 않는다.

## 9. 900문항 응답: 잘림만 해결해도 목표에 도달하는가

### 9.1 원래 정상 종료하던 군의 손실이 회복을 상쇄했다

F0의 종료 유형으로 군을 먼저 고정했다. 학습 모델의 결과에 따라 군을 다시 고르지 않았다.

| 고정 문항군 | 수 | v1 획득 / 손실 | v1 순변화 | v2 획득 / 손실 | v2 순변화 |
|---|---:|---:|---:|---:|---:|
| F0 length | 111 | 20 / 2 | +18 | 16 / 2 | +14 |
| F0 stop | 789 | 50 / 72 | −22 | 49 / 60 | −11 |

v2의 순증 3개는 **+14−11**이다. 이 분해는 관측값이며 +14 전부가 길이 제어의 인과 효과라는 뜻은 아니다.

| 실행 | length 종료 | 그중 정답 | NO_PARSE |
|---|---:|---:|---:|
| F0 8K | 111 | 2 | 121 |
| v1 | 82 | 1 | 104 |
| v2 | 98 | 6 | 111 |

v2의 오답 356개는 **정상 종료·PARSED 239개**, 정상 종료·NO_PARSE 25개, length·오답 92개다. 따라서 **남은 오답의 대부분은 답을 끝낸 뒤에도 틀린 경우**다. length 98개를 모두 오답이라고 세면 안 된다.

### 9.2 실제 응답 변화에는 여러 원인이 섞여 있다

샘플은 정오·종료 상태별 `SHA256('saved-audit-v1:'+ID)` 순으로 선택했고, 짧은 정상 종료 사례는 양쪽 1,200토큰 이하로 제한했다. 벤치마크 원문 전체나 새 풀이를 여기 싣지 않는다.

| ID | 관측 | 가능한 분류와 제한 |
|---|---|---|
| `Accounting_1` | F0와 v2가 같은 고정비·변동비 수치를 읽었지만 v2가 생산량 변화 시 고정비 단가 조정 규칙을 잘못 적용 | 실제 규칙 적용 퇴행 사례. 이미지 판독만의 문제가 아님 |
| `Psychology_20` | 내용상 같은 발달 단계를 설명하지만 짧은 명칭에 `stage`가 붙은 추출값이 V8에서 오답 | 표면 표현·고정 채점 효과. 지식 손실이라고 분류하면 안 됨 |
| `Biology_28` | 이미지 표시 위치에 대한 설명이 중앙 구조에서 측면 구조로 바뀌며 정답 획득 | grounding 변화 사례. Vision 모듈 단독 개선의 증거는 아님 |
| `Materials_21` | F0의 8K 미완결이 v2에서 3,040토큰의 정답으로 완결 | 끝맺기 개선 사례. 중간 과정의 전수 정확성은 미인증 |
| `Architecture_and_Engineering_9` | F0의 완결된 정답이 v2에서 8K 재해석·NO_PARSE로 바뀜 | 학습 후 잘림이 새로 생긴 역방향 사례 |

일부 다른 문항에는 정답 라벨과 이미지 의미 사이의 모호성도 있었다. 이를 모델 오류로 단정하거나 원래 점수를 바꾸지 않았다. 의학·약학 진단처럼 전문 검토가 필요한 사례도 이번 AI 열람으로 인증하지 않는다.

### 9.3 토큰 증가의 기대효과는 현재 자료만으로 계산할 수 없다

기존 B2에서 8,192토큰을 넘긴 것은 120개이고 그중 정답은 14개다. **같은 120개를 현재 8K F0와 v2는 각각 28개 맞혔다.** 이미지·GPU·동시 수·생성 궤적이 달라졌기 때문이다. 14개를 “8K라서 반드시 잃은 답”이나 “32K로 늘리면 되찾는 답”으로 계산하면 안 된다.

기존 R2의 length 75개와 B2의 length **90개**도 다른 실행의 값이다. 현재 문맥 길이는 실제 input+output 최대 F0 9,620, v2 10,814로 설정 24,576보다 작았다. 기록상 문제는 문맥 용량 부족이 아니라 생성 출력 한도 도달이다.

압축률이 높거나 줄이 다양하다고 유익한 추론이 계속되고 있다는 뜻도 아니다. 서로 다른 말로 동일한 후보를 반복 검토할 수 있다. 반대로 오래 생각했다는 이유만으로 전부 낭비라고 볼 수 없다.

**[제안]** 최종 제출 비교는 승인된 B2 조건으로 고정하되, 길이 증가를 새로운 지식 획득의 대체물로 기대하지 않는다. 비용을 쓰기 전 외부 개발 자료에서 정답 완결 시점·반복·정답률을 함께 본다. 토큰 상한이나 이미지 설정은 이번에 바꾸지 않았다.

## 10. 평가 조건과 v1 원인을 v2에 재사용하지 않기

F0/v1/v2의 900개에서 문제·보기·gold·유형·seed·P0·chat/messages·원본 이미지 참조·reference 전처리 size/grid·실제 엔진 prompt token ID·요청 sampling 설정의 차이는 없었다. 실제 `backend.json`의 동시 수는 **40**이다. 기본 resolved YAML의 32만 읽으면 잘못 보고하게 된다.

| 조건 | 기존 B2 | F0/v1/v2 8K 비교 |
|---|---|---|
| GPU | RTX 3090 | RTX 6000 Ada |
| 최대 출력 | 32,768 | 8,192 |
| 문맥 한도 | 40,960 | 24,576 |
| 이미지 픽셀 범위 | 1,003,520–4,014,080 | 262,144–1,310,720 |
| 실제 동시 요청 | 2 | 40 |
| 입력 차이 | 새 F0와 864/900개의 reference 전처리·엔진 prompt ID가 다름 | 세 모델 사이 해당 필드는 동일 |

F0/v1/v2는 기록상 같은 GPU 종류·driver·Python·Torch·Transformers·vLLM 버전이다. 다만 호스트 kernel과 wrapper commit은 다르다. 모든 문항에 `actual_engine_pixel_tensors_verified=false`이므로 reference pixel hash가 같다고 실제 엔진 pixel bytes까지 독립 인증했다고 쓰지 않는다. 가장 가까운 학습 효과 비교는 F0 541 대 v2 544지만 완전히 같은 하드웨어 실행의 결정론적 반복은 아니다.

또한 v2에서는 다음이 실제로 바뀌었다.

- 500문항 블록과 각 사분위에서 모든 10개 출처가 분포한다. **v1의 후반 출처 집중을 v2의 확인된 원인으로 쓰지 않는다.**
- 선형 LR 감소가 실행됐다. v1의 고정 LR을 그대로 원인으로 쓰지 않는다.
- 재풀이 학습 목표 중앙값 328토큰, T1 192, B 162다. v1의 정답을 본 수정 풀이 중앙값 98.5와 다르다.
- 전체 평가 출력 중앙값도 464.5로 회복됐다. **v2 실패를 “출력이 짧아져서” 하나로 설명할 수 없다.**

v2는 여러 요소를 동시에 바꿨으므로 어떤 변경이 출력 길이를 회복했는지도 단독 인과 효과로 확정하지 않는다.

## 11. SFT보다 RL이 좋은가: 관련 연구가 실제로 말하는 범위

사용자의 “smt”는 문맥상 SFT(supervised fine-tuning)를 뜻하는 것으로 해석했다.

| 연구 | 실제 근거 | 이 프로젝트에 적용할 때의 제한 |
|---|---|---|
| [STaR](https://arxiv.org/html/2203.14465v2) | GPT-J 6B가 자체 생성한 정답 풀이를 SFT하고, 실패 시 정답을 준 rationale도 활용 | 현재 v2에서 제외한 정답 조건부 풀이 학습을 포함한다. 텍스트 과제의 성과를 MMMU에 그대로 옮길 수 없음 |
| [SCoRe](https://arxiv.org/html/2409.12917v2) | 자기 생성 수정 trace의 offline SFT가 분포 불일치·행동 붕괴를 겪고, 온라인 다중 턴 RL이 개선하는 사례 | Gemini 계열의 텍스트 수학·코딩, 두 번 응답하는 자기수정 과제다. P0 한 번의 성능 향상과 다르며 논문의 test 재분할도 MMMU에 적용 금지 |
| [SFT Memorizes, RL Generalizes](https://arxiv.org/html/2501.17161v2) | Llama-3.2-Vision-11B의 카드 산술·길찾기에서 규칙·시각 변화에 RL이 더 잘 일반화 | 통제된 좁은 환경과 검증 피드백 실험이다. 모든 SFT가 대학 전공 문제에 실패한다는 일반 법칙이 아님 |
| [Debunk the Myth of SFT Generalization](https://arxiv.org/html/2510.00237v1) | 고정 프롬프트의 의미에 과적합하는 문제를 분리하고 지시 다양화·CoT로 SFT 일반화 개선 | CoT는 RL 학습된 Qwen3-8B가 생성한다. 상위 모델 설명 금지 조건에서 그 데이터 생성법은 사용 불가 |
| [RL Fine-Tuning Heals OOD Forgetting in SFT](https://arxiv.org/html/2509.12235v1) | SFT 초기에 좋았던 OOD 능력이 후반에 감소하고 RL이 제한적으로 복구하는 현상 | 다른 모델의 full-parameter 통제 실험. 300→3,417 악화와 양립하지만 우리 모델의 망각을 입증하지 않음 |
| [Rethinking Generalization in Reasoning SFT](https://arxiv.org/html/2604.06628v1) | 데이터 질·기저 능력·최적화에 따라 더 긴 SFT에서 하락 후 회복도 관측 | 반대로 “짧게 학습하면 항상 낫다”도 일반 법칙이 아님. teacher-free 멀티모달 오답노트 실증과는 다름 |
| [RLVR의 추론 범위 연구](https://arxiv.org/html/2504.13837v4) | 연구한 설정에서 pass@1 상승과 높은 k의 해결 범위 감소를 함께 관측; 시각 추론 실험도 포함 | RL이 기존 정답 경로의 확률을 높일 수 있으나 전문지식을 무조건 새로 만드는 것은 아님. 논문의 pass@k 진단은 우리 best-of-N 허용 근거가 아님 |
| [MM-Eureka](https://arxiv.org/html/2503.07365v2) | Qwen2.5-VL 7B/32B의 규칙 보상 기반 멀티모달 수학 RL | 문항당 8 rollout·온라인 필터링. 현재 단일 표본 학습 정책에서 그대로 적용 불가; 대학 30과목·Qwen4B 결과 보장 없음 |
| [DAPO](https://arxiv.org/html/2503.14476v1) | 긴 출력 RL에서 길이·잘림·정규화·entropy 문제를 분석 | 32B 수학 모델, 문항당 16응답, avg@32 등 다른 조건. 데이터 변환·다중 생성 선별까지 그대로 복사하면 현 규칙과 충돌 |
| [Qwen3-VL 기술 보고서](https://arxiv.org/html/2511.21631v2) | SFT·strong-to-weak distillation·RL 결합, 다양한 검증 가능 과제 사용 | 소형 모델의 teacher 학습, 235B 모델의 16응답 선별이 포함된다. 공식 개발법 전체를 이번 제약에서 재현할 수 없음 |

**판단:** RLVR는 `P0 입력 → 단일 정답`을 직접 보상한다는 점에서 현재의 정답 조건부 노트 SFT보다 목표에 직접 연결될 수 있다. 그러나 현재 채점기 오류를 보상으로 쓰면 정답 풀이에 잘못된 보상을 주며, 쉬운 분류형 자료에 RL을 적용해도 대학 지식 부족은 남는다.

현재 한 번 생성 원칙을 유지하면서 고려할 수 있는 것은 **단일 rollout의 policy gradient와 적절한 baseline/보존 제약**이다. 다만 단순 group-relative 방법에서 그룹 크기를 1로 줄이면 그룹 내 상대 advantage가 0이 되는 문제가 있다. 기존 GRPO류 설정의 `n=1` 변경만으로 같은 알고리즘을 얻는다고 생각하면 안 된다. 보상·baseline·정규화·off-policy 여부까지 별도 설계가 필요하다.

GRPO/SAPO/DAPO 등의 여러 rollout을 사용하고 싶다면 **학습 쪽 다중 생성 허용 범위를 사용자가 명시적으로 바꿔야 한다.** 평가의 단일 답 원칙은 유지한다. 예전 notebook RL의 갱신 성공이나 재시도 회복을 새로운 첫 시도 정확도 개선으로 재해석하지 않는다.

## 12. 데이터 교체·다양화: 기존 TRAIN 자료 중 무엇이 더 적합한가

현재 정책은 기존 데이터셋만 사용하고 자체 문제를 생성하지 않는 것이다. 따라서 아래는 **기존 TRAIN 후보 조사**이며 다운로드·도입·권리 승인·오염 전수검사가 완료됐다는 뜻이 아니다. 데이터셋 이름이 benchmark여도 허용된 train인지와 MMMU/Pro 파생인지가 핵심이다.

|---|---|---|---|

공개 교과서도 자동으로 안전한 대체물이 아니다. MMMU는 교과서·시험에서 수집됐으므로 같은 문장·그림 가족의 재유입 가능성이 있다. 예를 들어 [OpenStax 공식 권리 안내](https://help.openstax.org/s/article/Licensing-information-of-OpenStax-textbooks)를 확인하더라도 기존 TRAIN split과 데이터 구축 승인이 별개다. 원래 문항을 바꿔 쓰거나 숫자·이미지만 바꾸는 것도 오염을 해소하지 않는다.

## 13. “제대로 된 오답노트 학습”으로 발전시키는 설계안

### 13.1 세 가지 목표를 따로 관리한다

1. **정확한 노트:** 실제 오류를 찾고 맞는 사실·규칙으로 설명하는가.
2. **교훈의 도움:** 정답 누설 없이 교훈을 받은 재풀이가 나아지는가.
3. **가중치 전이:** 노트와 교훈을 전혀 받지 않는 새로운 P0 문항의 첫 답이 나아지는가.

현재는 노트 형식·가중치 변경·재로딩은 확인했지만, 1의 전수 정확성, 2의 대조 효과, 3의 전체 MMMU 개선은 확보하지 못했다. 세 지표를 한 개의 PASS로 합치지 않는다.

### 13.2 최소 변경으로 먼저 검토할 설계

| 순서 | 제안 | 미래 변경 후보 위치 | 수용 기준의 방향 |
|---|---|---|---|
| 1 | 학습 답 유형별 추출·비교 계약 정리 | `notebook_rl/answers.py`, `verifier.py`, 자료 adapter | 정답 범위·단위·alias·오답 반례 모두 보존; 과거 점수 덮어쓰기 없음 |
| 2 | 교훈 누설을 전체 이름뿐 아니라 alias·약어·의미로 점검 | `error_note/contract.py:hint_leak`, 수집 원장 | 알려진 누설 사례를 통과시키지 않고 불확실을 별도 처리 |
| 3 | 노트의 형식과 내용 확인을 분리 | `contract.py:build_rows_v2`, `collect.py` 및 확보 가능한 출처 주석 조사 | 검증된 사실·내부 모순·미확정을 기록; 틀린 노트를 임의 수정해 통과시키지 않음 |
| 4 | A/B 비중과 짧은 답의 계약 재설계 | `train.py:run_update`, `protocol.py`, 행 생성 정책 | 노트가 목표 행동을 압도하지 않게 사전 가중치 지정; 길이만으로 품질 인증하지 않음 |
| 5 | 실제 작업별 데이터 구성과 기록 수정 | 기존 adapter·order·manifest 도구 | Sociology hash 라벨 같은 허위 범위 주장 제거; source 순환과 task 균형 구분 |
| 6 | 필요하면 직접 결과 보상 RL 비교 | 기존 `notebook_rl` 재사용 가능성 검토 | 검증기 신뢰성 선행, 단일 응답 목표와 보상 일치, 기존 기능·효과 기록 분리 |

새 trainer나 복잡한 reward framework를 우선 만들 필요는 없다. 현재 존재하는 경로에서 위의 계약을 바로잡는 것이 먼저다. 이 표의 코드 변경은 이번에 수행하지 않았다.

### 13.3 SFT 다음 후보

**[제안]** 새로 검증한 자료에서 `P0 → 올바른 풀이`를 중심으로 하고 노트를 보조 목표로 둔다. 현재 68.5%의 노트 계수를 낮추는 것은 검토 가치가 높지만, 최적 비율을 현재 로그에서 알아낼 수는 없다. 예를 들어 10~20% 같은 값도 실측 최적값이 아니라 사전 등록 후보일 뿐이다.

원래 틀린 문제를 어떻게 다시 풀었는지가 명확한 풀이를 충분히 확보하지 못하면 대규모 학습으로 넘어가지 않는다. 반대로 정답만 아는 상태에서 모델이 꾸민 긴 설명을 질 좋은 CoT라고 취급하지 않는다. 길게 쓰기, 짧게 쓰기 어느 쪽도 목표가 아니다.

기존 능력 보존을 위한 소량의 서로 다른 작업 자료도 필요하다. 쉬운 자료를 전부 버리기보다 유지 목적과 새로운 추론 학습 목적을 명시적으로 분리한다. 분포·가중치·학습량을 동시에 크게 바꾸고 원인을 한 가지로 설명하는 실험은 피한다.

### 13.4 RL 다음 후보

**[제안]** 채점과 데이터 신뢰성을 확보한 뒤, 동일한 P0 첫 답을 직접 보상하는 teacher-free RL을 작은 범위에서 비교한다. 보상은 최종 정답 중심이고, 검증 가능한 이미지 사실·계산을 보조적으로 쓸 수 있다. 정답인 듯한 노트 문체·자기 신고·긴 출력 자체를 보상하지 않는다.

단일 rollout을 유지하려면 적절한 baseline이 있는 policy-gradient 설계가 필요하다. 미확정 풀이를 잘못된 답으로 일괄 처벌하거나, 모든 응답의 보상이 같은데 가짜 advantage를 만들지 않는다. 기존 참조 모델에 대한 보존 제약은 후보지만 계산 비용과 실제 망각 방지 효과는 별도 확인해야 한다.

학습 쪽 다중 rollout을 새로 허용하지 않는 한 문헌의 GRPO·DAPO 성과를 그대로 기대할 수 없다. 허용하더라도 평가의 단일 답, 고정 seed, arm당 사전 지정 checkpoint는 유지하며, 추가 비용을 먼저 산정해야 한다.

## 14. 다음 실험을 한다면: 원인 하나씩 분리하는 순서

이 절은 **실행 계획 제안**이다. 지금 실행 허가를 요청하거나 실행을 시작한 것이 아니다.

| 단계 | 질문 | 최소한의 대조 | 진행/중단 판단 |
|---|---|---|---|
| A. CPU·원장 계약 확인 | 거짓 실패·정답 누설·내용 모순을 걸러낼 수 있는가 | 이번에 찾은 실제 사례와 정상/오답 반례를 향후 검사로 사용 | 기본 계약이 틀리면 새 GPU 학습 중단 |
| B. 작은 실제 생성 확인 | 바뀐 지시가 답만 쓰기·교훈 언급·새 누설을 유도하지 않는가 | 결과를 보기 전에 고정한 외부 문항·출처별 표본 | 형식 성공뿐 아니라 유효 A의 수·출처·길이·정확성을 확인 |
| C. 노트 효과 분리 | 같은 풀이에서 노트가 추가 이득을 주는가 | A만 학습 대 같은 A+검증된 B; 공통 A 노출·학습 모듈/경로·optimizer step·LR·순서를 맞춤 | 외부 고정 평가의 첫 답 이득과 유지 능력 손실을 함께 보고 |
| D. 데이터 효과 분리 | 출처·형태 개선이 이득을 주는가 | 같은 학습법에서 사전 고정한 기존/개선 자료; 유효 감독 토큰·업데이트 예산도 보고 | 학습 loss 감소만으로 확대하지 않음 |
| E. SFT/RL 비교 | 정확한 보상으로 직접 최적화하는 편이 나은가 | 같은 출발점·자료·P0 평가·가능한 한 같은 생성/계산 예산, 각 arm 한 checkpoint | 과거 RL 기능 PASS를 효과 PASS로 재사용하지 않음 |
| F. 최종 확인 | 전체 validation에서 보존을 포함한 순이득이 있는가 | 사전 지정 모델을 승인된 F0/B2 조건과 비교 | 전체 900·단일 답·고정 V8; 342개만으로 일반화하지 않음 |

**주의:** A-only와 A+B를 비교할 때 현재처럼 행 수 분모가 달라지면 A의 상대 세기도 바뀐다. 기존 `solution` arm은 Vision까지 끄므로 그대로 순수 대조군으로 재사용할 수 없다. 공통 A 항의 계수·노출·경로를 맞추고 B 추가가 늘리는 비용을 별도로 기록해야 “노트의 효과”를 해석하기 쉽다. 경로 정책 변경은 별도 설계 결정이다. SFT와 RL도 같은 update 수만 맞춘 것으로 계산량이 같다고 할 수 없다.

교훈 자체 효과를 분리하려면 외부 자료의 같은 재풀이 seed에서 교훈 유무 대조가 필요하다. 이것은 현재 1회 재풀이 제한과 다른 추가 생성 실험이므로 **별도 승인 범위를 명시**해야 한다. 평가 답을 둘 중 좋은 것으로 선택하지 않는다.

이미 존재하는 외부 dev 402·sealed 209는 후보지만 현재 학습 source에 가까워 대학 수준 전이 전체를 대표하지 않는다. 동일 이미지·문서·가족을 분리한 외부 유지/전이 평가를 먼저 고정한다. 여러 checkpoint의 최고점을 고르는 대신 각 arm의 평가 checkpoint와 종료 조건을 사전 지정하고, dev는 계획한 go/no-go에 쓴다. 추가 arm·seed·새 학습·새 900평가는 각각 사용자 실행 범위가 필요하다.

300 모델의 나머지 558 평가를 한다면 “초기 소량 학습이 이미 맞히던 문제를 얼마나 잃었는가”라는 질문에 답한다. 현재 자료만으로 비용·소요시간을 확정하지 않는다. 그 실행은 노트가 유효하다는 인증이나 67.4 달성 계획을 대신하지 않는다.

## 15. 62와 67.4를 넘기 위한 현실적인 우선순위

1. **현재 실패를 잘못 읽게 만드는 학습 채점·정답 누설부터 해결한다.** 이 상태에서는 SFT/RL 비교도 왜곡된다.
2. **오답에서 실제로 새로 확보한 올바른 풀이를 늘린다.** 단순히 B 노트의 개수를 늘리는 것과 구분한다.
3. **분류·단답·쉬운 템플릿 중심 분포를 관측+계산+규칙 적용 자료로 보완한다.** TAT-DQA·ChartQA-H를 우선 조사하되 권리·오염·TRAIN·라벨 원천을 새로 확인한다.
4. **기존 능력 손실을 동시에 줄인다.** 전체900의 +65/−62 구조에서는 회복만 늘리고 보존을 무시하면 목표에 도달하기 어렵다.
5. **노트 SFT와 직접 보상 RL은 품질이 확보된 동일 조건에서 비교한다.** 논문 제목을 근거로 알고리즘부터 교체하지 않는다.
6. **최종 목표 조건을 고정한다.** 8K 실험, B2 32K 제출 조건, 공식67.4는 별도로 보고한다. 한도를 늘린 점수 상승을 학습 이득과 섞지 않는다.

**현재 증거로 67.4 초과를 약속할 수는 없다.** 다만 다음 비용을 어디에 써야 하는지는 더 명확해졌다. 새로 발견한 채점·누설 결함을 방치한 채 노트를 더 만들기보다, 독립 해결에 필요한 신호와 데이터 범위를 먼저 바로잡는 것이 근거가 강한 순서다.

## 16. 구현·테스트·실행 작업 계획 — 작성 당시 기준

이 절의 `NOT_STARTED`·미실행 표기는 계획 작성 당시 상태다. 후속 실행 승인과 실제 진행 상태는 §17을 따른다. 계획 항목의 존재를 검사 통과나 성능 향상 증거로 읽지 않는다.

### 16.1 이번 변경의 목표와 경계

**첫 구현 목표는 새 SFT 경로의 학습 신호를 신뢰할 수 있게 만드는 것이다.** RL 구현은 첫 변경에 넣지 않는다. 가칭 `v3`는 확정된 성과나 이미 존재하는 CLI 이름이 아니라 아래 변경을 구분하기 위한 새 protocol 제안이다.

권고 기본값은 원본 F0에서 시작, 첫 풀이 1회, 정답을 보고 자기 노트 작성, 누설 없는 교훈으로 오답 문항 1회 재풀이, `P0 → 채택 풀이`와 검토된 노트의 손실 계수 0.9/0.1이다. 평가 입력에는 노트·교훈·정답을 주지 않는다. 교훈 유무를 따로 반복 생성하는 실험은 첫 구현 범위에서 제외한다.

### 16.2 작업 순서와 병렬로 할 수 있는 일

```text

  ├─ S1. 학습용 채점 + 누설/노트 감사 계약
```

### 16.4 구현 전에 고정할 여섯 가지 계약

**C1. 학습용 정답 판정**

- 추출은 gold를 보지 않고 하나의 명시된 답을 고른다. reasoning 전체에서 gold 문자열을 찾거나 여러 숫자 중 맞는 것을 고르지 않는다. 같은 응답에서 gold만 바꾸어도 추출값은 같아야 한다는 변형 검사도 포함한다.
- 범위는 범위로, 단위는 단위로 다룬다. `60°`와 `60 rad`를 단순 기호 제거로 같게 만들지 않는다. 단위 변환·오차·alias는 원출처에서 확인해 사전에 고정한다.
- 같은 숫자가 있어도 다른 단위·부호·범위 끝점·복수 답이면 정답으로 통과시키지 않는다. 처리할 수 없는 구문은 `UNVERIFIABLE`로 보존한다. “모델이 틀렸다”와 구별한다.
- 기존 `VerifierResult` 구조를 바꾸지 않는다. 자세한 판정 근거는 별도 receipt에 저장한다. `UNVERIFIABLE`이 note prompt로 들어갈 때도 이를 지식 오답으로 바꾸지 않도록 분기·skip 사유를 구현한다.
- 과거 T1 raw의 재사용은 새 규칙으로 별도 채점 원장을 만드는 경우에만 검토한다. 잘못된 피드백에 조건화된 과거 note/resolve는 새 경로에 자동 재사용하지 않는다.

**C2. private 출처 근거 파일(sidecar)**

문항 ID, 원본 vault/이미지/actor hash, source/revision/train/native ID, 허용 답 형식·alias·단위 규칙, 사실 주석의 원본 필드/위치/hash, HUMAN/PROGRAM 계보, 검토 방식·범위를 담는다. AI 검토는 `human_verified=false`다. 원본에 없는 지식·관측을 새 사실로 만들어 채우지 않는다.

현재 공개 데이터 adapter는 관측 slots·oracle facts를 비워 두므로, 기존에 완성된 내용 검증기가 있다고 가정할 수 없다. S0에서 source별로 **실제로 확보할 수 있는 주석**을 확인하고 지원 범위를 정한다. private 파일은 기존 guard에 차단 경로를 추가하는 방식으로 보호하며 frozen guard 자체는 고치지 않는다. actor/resolve는 그 내용이나 gold alias를 읽지 않는다.

**C3. 노트와 Lesson의 별도 수용**

- 노트 형식 PASS, 내용 감사 PASS, 교훈 누설 CLEAR를 별도 필드로 기록한다. 최종 답 정답이나 모순 미검출만으로 노트 내용 PASS를 만들지 않는다.
- 자동 검사는 출처가 지원하는 사실·산술·명시 모순에 한정한다. 나머지는 UNKNOWN이다. B 원문 전체를 학습하려면 검사 범위를 덮는 출처 근거 또는 명시 검토 receipt가 있어야 한다. 일부 주장 검증을 자유 설명 전체 인증으로 확대하지 않는다.
- Lesson은 정답의 약어·동의어·다른 보기 이름 및 의미상 정답 암시를 별도로 살핀다. 문자열 검사만으로 일반적인 의미 누설까지 해결됐다고 말하지 않는다. 미확정 교훈은 재풀이에 전달하지 않는다.
- 노트 B에서 정답을 언급하는 것은 허용된 gold-conditioned 학습과 구분한다. 그것이 Lesson의 정답 비노출을 허용하는 근거는 아니다.
- 노트 원문·T1·sidecar·audit SHA와 판정 범위를 묶는다. 크기가 같은 note 변조도 차단한다. resolve에는 허용된 Lesson과 그 receipt만 전달하며 gold가 든 note를 다시 열지 않는다.
- 불량 노트를 고쳐 쓰거나 일부 답을 수작업으로 보충해 통과시키지 않는다. 충분한 B를 검토할 근거가 없으면 해당 범위를 `CONTENT_VALIDATION_PENDING`으로 보고하고 노트 학습 확대를 중단한다.

**C4. A행·길이·경로**

A는 정상 종료한 정답 T1 또는 정답 재풀이의 원문이다. A2의 생성 입력에는 교훈이 있지만 학습 입력은 힌트 없는 P0이며, 입력·출력 원문 SHA를 연결한다. 정답을 본 수정 풀이는 계속 학습하지 않는다.

32토큰 최소 길이는 일괄 해제하지 않는다. 원래 단답을 요구하는 작업은 별도 유형으로 집계하고, 첫 추론 실험의 A 주 감독에 넣을지 자료 등록 때 결정한다. 최소 길이·4,096토큰 상한·반복 기준의 변경은 source/task 계약별 새 protocol 항목이며, 합격률을 보고 사후 조정하지 않는다. 정상적인 짧은 답에 군더더기를 붙여 학습시키지 않는다.

첫 대조에서는 기존 자기 신고 기반 FULL/LM 규칙을 양 arm에 동일하게 적용한다. 노트 내용 검토가 시각 모듈의 인과 진단을 대신하지 않는다. Vision/Merger 동결 비교는 별도 후속 실험이다.

**C5. 90:10 수식과 공정한 no-note 대조**

각 행의 `ℓ`은 목표 응답과 EOS token의 평균 NLL이다. 한 갱신에서:

```text
NOTE:    L = 0.9 × mean(ℓ_A) + 0.1 × mean(ℓ_B)
NO-NOTE: L = 0.9 × mean(ℓ_A)
```

- B가 없으면 그 항은 0이며 A를 1.0으로 재정규화하지 않는다. 이것은 수식상 계수이고 실제 gradient/update의 90:10 인증이 아니다.
- 양 arm은 같은 A의 prompt·target·route·순서·노출, 동일 초기 F0/adapter seed, optimizer·LR·update 목록을 사용한다. 기존 `solution` arm은 route를 바꾸므로 이 대조에 사용하지 않는다.
- encoding 검사까지 완료한 공통 admission manifest를 먼저 고정한다. 원래 16문항 그룹 중 **A가 하나 이상 있는 그룹**만 양 arm의 update 목록에 넣는다. A가 없는 그룹은 양쪽 모두 비활성화하고 해당 B와 이유를 원장에 남긴다. NOTE만 추가 optimizer step을 수행하지 않는다.
- 고정 이후 메모리·길이 등의 사유로 새 행이 탈락하면 실행을 멈춘다. 조용히 서로 다른 A 또는 step 수로 계속하지 않는다.
- group별 nA/nB, 토큰 수, 실제 분모·행 계수, raw/weighted loss, route, 비활성화 사유를 기록한다. scheduler는 공통 유효 update 수로 만든다.
- CPU에서는 clip 이전 NOTE gradient가 A항과 B항 gradient의 합인지, B 계수가 0일 때 공통 A항과 일치하는지 확인한다. gradient clipping·Adam 이후의 update 비율을 90:10이라고 해석하지 않는다. A가 없는 그룹을 제외하는 첫 설계는 어려운 노트 전용 그룹의 효과를 검증하지 못하므로 그 수와 적용 한계를 보고한다.

**C6. 재개·동결·기록**

protocol·grader·note instruction·audit 규칙·sidecar·rows·admission·order·arm·정밀도·코드 SHA를 binding에 포함한다. 하나라도 달라지면 기존 실행에 resume하지 않는다. 새 실행을 별도로 만든다. 노트 지시 한 줄을 바꿔도 기능시험 receipt는 새 조건에서 다시 확보한다. optimizer·scheduler·RNG·cursor를 포함한 재개를 확인하며 중간 checkpoint는 복구용이고 성능을 보고 고르는 용도가 아니다.

### 16.5 CPU 검사 목록과 판정 기준

실제 데이터·벤치마크 원문을 공개 fixture에 넣지 않는다. 공개 CPU fixture는 기능 검사용 작은 자체 예제이며 **학습 데이터로 사용하지 않는다**. 실제 실패 사례의 원문 검사는 private 경로에서 따로 기록한다.

| 검사군 | 반드시 포함할 양성·음성 사례 | 통과 조건 |
|---|---|---|
| 정답 추출/비교 | 단일 범위·음수·소수·분수·boxed 숫자·도/면적 단위·등록 alias; 틀린 단위·범위 endpoint·복수 후보·정답의 부분 문자열 | 사전 기대 판정과 일치. 미지원은 UNKNOWN/UNVERIFIABLE, 정답으로 추측하지 않음 |
| legacy 호환 | v1/v2 prompt·rows·protocol·기존 typed 비교·V8 계약 | 기존 입력의 기대 결과/identity 유지. 새 버전을 고르지 않으면 새 규칙 미적용 |
| 누설 | 전체 보기 이름·약어·alias·우회 답 표현; 일반 단어·관사 A·음계·화학기호 등 오탐 반례 | 알려진 TYLCV 유형 누설 수용 0. 불확실을 CLEAR로 승격하지 않음 |
| 노트 감사 | 출처 사실 일치/불일치, Cause와 본문 모순, 출처 주석 없음, 일부만 검증된 자유 설명 | 지원 범위를 기록하고 미확정 B를 사실 검증 PASS로 수용하지 않음 |
| 무결성·격리 | 같은 크기의 note 변조, 잘못된 ID/sidecar/hash, forged 추출값, actor의 private 파일 읽기 | 잘못된 연결·권한 접근 거부. gold·alias가 T1/resolve prompt에 없음 |

| loss 수식 | 서로 다른 행/토큰 수, A만/B만/혼합, 다른 미니배치 분할 | 독립 계산한 수식·gradient와 수치 허용오차 안에서 일치. A의 계수/경로가 두 arm에서 동일 |
| gradient/mask | prompt·이미지·오답 입력 마스크, target/EOS, FULL/LM 단독·혼합 | 직접 loss 대상 정확, LM-only에서는 V 변화 없음, FULL 경로의 기울기 보존 |
| 학습 상태 | 유한 loss/gradient, 빈 학습 목록, 비유한 수치, 중단·연속/재개, 바뀐 protocol로 resume | 조용한 skip/NaN 진행 없음. 새 규칙으로 옛 실행 재개 거부 |
| planner/Pod | 새 flag 자식 전달, pin/admission/audit 누락, 잘못된 arm·stage, private bundle·공개 파일 검사 | 누락 receipt로 다음 단계 미진입, 계획 생성이 실행하지 않음 |
| export/평가 참조 | checkpoint·merged metadata·model_ref 불일치, 잘못된 split/seed/arm | 잘못된 평가 참조 거부. 고정 P0/V8 의미 불변 |

### 16.6 로컬과 클라우드의 기능시험

**로컬 NF4 — 성능 향상 문턱이 아닌 기능 확인**

1. 사전 고정한 기존 외부 데이터 2문항으로 T1 → 올바른 grade → note/audit → 허용 시 resolve → rows → 실제 update → 저장 → 별도 프로세스 reload를 확인한다.
2. 고정 10문항에서 같은 경로와 두 학습 arm을 확인한다. FULL/LM, A2, B가 실제로 발생했는지 각각 기록한다. 발생하지 않은 분기를 통과했다고 쓰거나 성공 문항으로 교체하지 않는다.
3. 기존 loss/gradient 유한성·base 동결·실제 학습 텐서·optimizer/cursor·재로딩 기준을 유지한다. 기존 reload의 `max |Δ logp| ≤ 1e−3`와 greedy 일치 여부를 기록한다. CPU fixture와 실제 Qwen 결과는 분리한다.
4. 학습으로 새 정답이 늘어야 기능시험이 통과하는 것은 아니다. 다만 A2/B가 전혀 없으면 오답노트 경로의 실제 연결은 미검증이므로 본학습으로 확대하지 않는다. 부족한 분기의 확인 방법을 별도로 정한다.

**클라우드 BF16 — 실제 본학습 경로 확인**

1. 승인된 GPU·시간·가격 범위, 실제 잔액·회수 예약금·watchdog, clean 고정 commit·lock·모델/자료 hash를 먼저 고정한다. 새 유료 실행은 별도 지시 전 시작하지 않는다.
2. 원본 BF16에서 고정 10문항 경로를 확인한다. 재로딩 후 checkpoint와 merged export에 L/V와 네 Merger가 모두 포함되는지 확인한다.
3. PyTorch unmerged ↔ merged ↔ vLLM의 고정 비벤치마크 probe를 비교한다. **새 프로세스 reload의 1e−3를 다른 backend의 합격 기준으로 그대로 복사하지 않는다.** F0 경로의 수치 차이를 먼저 측정하고, 허용오차·greedy/최종답 비교 범위를 학습 결과를 보기 전에 고정한다. 실패하면 원인을 조사하며 사후 허용오차 확대를 하지 않는다.
4. 실제 prompt ID·가능한 전처리 텐서·모델 hash를 기록한다. 엔진 pixel bytes를 확인할 수 없으면 미검증 필드로 남긴다.
5. 기능 probe의 반복 출력은 동등성 확인용이며 점수 산출·좋은 답 선택에 쓰지 않는다. 해당 반복도 실행 계획에 명시한다.
6. **어떤 프롬프트·필터·학습 계약이라도 바꾸면** 그 변경을 포함한 새 commit으로 영향받는 CPU 및 작은 실제 기능시험을 다시 거친다. 확인 없이 전체 수집으로 진행하지 않는다.

### 16.7 데이터 교체와 300문항 효과 시험

**데이터 준비:** S2에서 TAT-DQA/ChartQA-H의 권리·원래 train·라벨 계보·이미지/문서 가족·MMMU/Pro 모든 split 제외를 확인한다. 새 데이터 취득·사용 범위는 확정 전이다. MMK12/UniGeo의 미해결 사항을 확인한 것처럼 채우지 않는다. 현재 지원 source만으로 사실 검증이 가능한지 먼저 보고하고, 없으면 데이터 계약 준비 단계에서 멈춘다.

source별로 실제 작업·원래 난도·답 형태·필수 관측·계산 주석의 유무를 집계한다. 같은 회사/보고서/차트/문제 가족은 train/dev/sealed에 나누지 않는다. 생성 결과를 보고 좋은 문항으로 바꾸지 않는다. 고정 300개 ID, 순서, source/task 배분, 외부 유지·전이 평가 ID, 오염/권리 receipt를 **생성 전에** pin한다. 실제 후보 검토 전에는 문항 ID나 과목별 수를 만들어 적지 않는다.

**첫 비교:** 같은 300개에서 얻은 공통 A와 감사된 B로 원본 F0부터 다음 두 학습 arm을 각각 시작한다.

- `NOTE`: C5의 0.9 A + 0.1 B.
- `NO-NOTE`: 같은 A·같은 경로·같은 0.9 계수, B만 없음.
- 평가 기준점은 같은 조건의 F0다. 기존 v2나 소량 학습 checkpoint를 출발점으로 사용하지 않는다.

첫 비교는 **같은 데이터에서 노트 추가 효과**를 보는 것이다. 새 데이터와 학습법을 동시에 바꾼 결과를 과거 v2와 비교해 데이터 효과까지 분리됐다고 말하지 않는다. 기존/개선 데이터의 별도 대조나 RL arm은 필요한 경우의 후속 실험이며 첫 유료 실행에 무조건 추가하지 않는다.

노트 B 전체의 검토가 가능하지 않으면 부분 검토 수·출처·UNKNOWN 수를 먼저 보고한다. B=0인 실행을 “오답노트 방법 시험 완료”로 표시하지 않는다. 검증 가능한 노트를 늘리기 위해 상위 모델에게 설명을 대신 작성시키거나 실패 응답을 수정하지 않는다.

**기능·효과·비용 gate를 분리한다.**

| gate | 판단 |
|---|---|
| 계약/기능 | 알려진 누설·형식 오류 반례 기대일치, 원문/receipt/격리 확인, 유한 update·실물 저장·fresh reload. 작은 기능시험에서 정확도 상승은 요구하지 않음 |
| 유효 감독량 | source/task별 A1/A2/B, 실제 검토 범위, 누설·UNKNOWN·짧음·반복 탈락, kind별 손실 계수를 보고. 이 단계의 최소 유효량은 실제 source 지원 범위를 확인한 뒤 생성 전 등록 |
| 전체 효과 | 고정 외부 평가의 NOTE−F0 짝 차이와 구간, 유지/전이 묶음별 손익을 함께 보고. 높은 점추정만으로 개선 입증하지 않음 |
| 노트 추가 효과 | NOTE−NO-NOTE의 같은 문항 짝 차이와 구간. 같은 A 노출·경로·update가 아니면 노트 단독 효과라고 보고하지 않음 |
| 확대 여부 | 양의 근거가 부족하거나 구간이 0을 포함하면 `INCONCLUSIVE/HOLD`, 하락·신뢰성 결함이면 `FAIL`. 효과 목표·허용 유지 손실은 평가 ID와 함께 사전 등록. 불확정을 실패 은폐나 자동 증액 사유로 쓰지 않음 |

평가의 독립 단위는 이미지·문서·가족 구조를 반영해 정한다. 같은 이미지의 여러 질문·여러 seed를 독립 표본으로 무조건 합치지 않는다. CI·검정법·주 지표·arm당 checkpoint·중단 기준은 평가 결과를 보기 전에 고정한다. NOTE−F0와 NOTE−NO-NOTE 양쪽의 통계적 개선을 주장한다면 다중 비교 처리도 사전에 정한다. 첫 고정 실행의 구간은 seed·재학습 변동을 모두 측정한 것이 아니다. 90:10을 여러 비율 중 최고 MMMU 점수를 고르는 방식으로 조정하지 않는다. 최종 후보는 NOTE로 사전 지정하며, 대조군 점수가 높다는 이유로 사후에 NO-NOTE로 교체하지 않는다. 대조군 채택은 별도 후속 계획이다.

### 16.8 본학습·최종 900평가·회수

- 300문항 기능/효과/비용 판단과 사용자 실행 범위를 확인한 뒤에만 승인된 본학습 규모를 시작한다. 숫자를 맞추려고 미검증 자료로 3,417개를 채우지 않는다.
- 본학습은 원본 F0에서 사전 등록한 전체 목록·한 학습 일정으로 시작한다. 300 모델을 이어 학습할지에 따른 교란을 없애기 위한 제안이다. epoch·유효 step·LR·A/B 계수는 시작 전에 고정한다.
- arm당 평가 checkpoint는 하나이며 중간 checkpoint는 복구용이다. loss가 낮거나 MMMU가 높은 중간 모델을 골라 제출하지 않는다.
- 최종 승인된 모델은 MMMU validation 전체 900문항, 문항당 답 하나, 고정 seed 3407·P0·V8로 평가한다. 342/558 분해는 진단이고 전체 합계가 주 결과다.
- **62점 초과 판정은 최소 559/900, 67.4 수치 초과는 최소 607/900**이다. 공식67.4와 단일 비율을 비교하는 검정으로 학습 효과를 대신하지 않는다. 같은 조건 F0와 짝 차이도 보고한다.
- 이전 558의 B2 조건과 직접 비교하려면 32K·B2 이미지·동시 수 등 최종 protocol 변경을 별도로 확정해야 한다. 현재 8K 유지 결정은 이 문서만으로 해제되지 않는다. 8K로 계속 평가하면 그 결과와 B2의 차이를 그대로 표시한다.
- 실제 GPU와 동시 수가 달라진 F0 기록을 같은 조건 대조군으로 자동 재사용하지 않는다. 필요한 F0 재실행의 비용도 최종 실행 범위에 포함한다.
- 완료 후 remote manifest → local 수신·hash·정오/산술 재확인 receipt → 소유 Pod 종료 → 소유 storage 삭제 → 잔존 조회 순서로 정리한다. 회수 실패나 비용 한도 도달 때 자동 연장·재시작하지 않는다.

## 17. 실행 승인 반영 — 2026-11-03

후속 사용자 지시로 §16의 계획 → 코드 → CPU → 로컬 NF4 → RunPod BF16 순서의 실제 진행이 승인되었다. 앞 절의 ‘별도 실행 지시’는 이 승인 범위 안에서는 다시 묻는 절차가 아니다. 아래 제한과 단계 판정을 충족하며 계속 진행한다.
이는 최초 승인 기록이며, 현재는 후속 §17.2–17.4의 로컬 무갱신 진단 범위가 우선한다. RunPod와 GitHub 게시는 대기 중이다.

- 가용 예산은 사용자 제시 25달러이며, 실제 잔액·시간당 가격·저장소 비용을 실행 직전 조회한다. A40 또는 RTX 6000 Ada 48GB 중 시간당 1달러 이하 후보를 고르고 회수 비용을 남긴다. 예산을 넘는 자동 연장·추가 충전은 하지 않는다.
- 생성 상한 8192·이미지 262144–1310720·P0·sampling·seed·V8·단일 답 원칙을 유지한다. 최종도 8K다. 32K/B2 조건 변경은 이번 실행에 포함하지 않는다.
- 상위 모델의 풀이·튜터·학습 문제 생성 없이 Qwen 자신이 작성한 풀이·노트만 쓴다. 출처 근거 확인과 노트의 AI 검토는 새로운 풀이 작성과 구분하며 `human_verified=false`로 기록한다. 내용 미확정은 그대로 남기고, 그 노트 전체를 검증 완료로 학습시키지 않는다.
- 수치 비교의 기존 `abs_tol`/`round_to`는 동결된 adapter 판정 정책으로 보존한다. 이를 원자료 저자가 지정한 오차라고 표시하지 않는다. 새 단위·alias는 원자료 근거가 있을 때만 추가하며, 명시 단위 근거가 없으면 추측해서 채우지 않는다. §16 C1의 원출처 확인과 기존 판정 정책 보존을 이처럼 구분한다.
- 기존 vLLM 연속 요청과 메모리 기반 KV/동시 수, 학습 토큰 예산별 microbatch를 재사용한다. 학습·생성은 순차 단계로 수행하고, 각 단계 안에서 여러 문항을 처리한다. 메모리 부족을 이유로 토큰·해상도·BF16 조건을 낮추지 않는다.
- 300문항 시험 결과와 checkpoint/원장을 먼저 로컬로 회수해 무결성·노트 학습 경로·대조 효과를 검토한다. 본학습 gate를 통과해야 다음 단계로 간다. 검토·수정이 길어지면 회수 후 소유 Pod를 삭제하고 수정본을 GitHub에 게시해 새 Pod에서 clean clone한다.
- 최종 지정 checkpoint로 MMMU 900문항을 1회 평가하고 원문·집계·checkpoint를 로컬 회수한다. 559/900·607/900 수치 목표와 실제 달성 여부를 분리한다. 결과를 보고 좋은 checkpoint·seed·답으로 교체하지 않는다.
- 새 파인튜닝 코드는 `fine_tuning/`에만 둔다. `MMDL/` 및 고정 파일은 수정하지 않는다. 실험 저장소 `MMDL_test`의 명시 파일만 검토·게시하며 상위 작업공간의 기존 변경은 건드리지 않는다.

구현은 학습용 채점, 노트 감사/행 수용, 손실/재개를 파일 소유권을 나누어 병렬 진행하고 수집·계획 연결은 순차 통합한다. 검증 상태와 실제 실행 증거는 완료되는 대로 기록한다. **승인은 성공 증거가 아니며 현재 67.4점 초과는 여전히 미검증 목표다.**

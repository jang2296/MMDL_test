1. 본학습 시작이 평가 속도 측정(약 45분)과 평가 비용 자금 관문(29.23달러)에 묶여 있다. 평가 방식은 학습이 끝난 뒤에야 쓰인다.

## 3. 수정 A — 학습 체인 (학습 전에 필수)

### A1. `fine_tuning/error_note/plan.py`
- 새 stage `v17-train`: 기존 `v17-calibration`의 단계에서 `eval-throughput-calibration`(평가 속도 측정)을 빼고,
  `bf16-functional-calibration` 뒤에 `campaign-advance` → `evaluation-decision`(기존 `v17_eval decide`, DEGRADED는 정지)
  → `require-complete` → `reload`(새 프로세스) → `export`(비병합) → 새 단계 `training-artifact-seal`을 잇는다.
  한 job으로 끝까지 실행한다(사전 점검과 본학습 사이 수동 정지 없음).
- 자금: `[사용자 2026-11-17]` 금액 때문에 멈추지 않는다(9절). 학습 체인에는 예상 비용으로 시작을 거절하는 관문을 두지 않는다.
  학습 예상 시간은 새 params 키 `training_estimate_seconds`(v16b 실측 RL 7.28시간 기반 값, 근거 문자열 `training_estimate_basis` 필수)로
  기록·보고만 한다.
- 기존 `v17-calibration`·`v17` stage는 지우지 말고 남겨 과거 spec 재현을 보장한다(레거시 출력 바이트 불변 검사 유지).

### A2. `fine_tuning/error_note/v17_preflight.py`
- `bind_execution`을 둘로 나눈다.
  - `bind_training(args, plan)`: 코드 식별(`_identity`) + 기능 시험 영수증 + 비용 영수증. 평가 측정 영수증을 요구하지 않는다.
  - `bind_evaluation(args, plan)`: 학습 결과 영수증 + 평가 엔진 검증 영수증(아래 B) + 평가 커밋 식별.
- `campaign_v16b.py` main의 `require-complete`·`export`와 `advance`는 `bind_training`을 쓴다(학습 커밋에서 실행되므로 해시 검사는 그대로 통과).
- `trained_export_preflight`(최종 조정층 사전 점검)는 평가 체인으로 옮겨 `bind_evaluation`을 쓴다.

### A3. 학습 결과 영수증 `training-artifact-seal`
- 봉인 내용: 학습 커밋, 소스 해시, 캠페인 계획 SHA, 최종 체크포인트 메타·파일 목록 SHA, 내보낸 모델 `model_ref.json`과 파일 목록 SHA,
  재로딩 영수증 SHA, 기능 시험·비용 영수증 SHA, 평가 진입 결정 SHA.
- 평가 체인은 이 영수증의 파일 해시를 다시 계산해 일치할 때만 진행한다. 평가 커밋이 학습 커밋과 달라도 학습 결과는 해시로 연결된다.
- 허용 목록 검사는 보조로만 쓴다. 평가 커밋에서 프롬프트·채점·입력 변환·재개 동작에 관련된 파일(`src/mmdl/evaluation/*`, eval config, prereg 형식)이
  학습 커밋과 같은지 해시로 확인하고 기록한다.

## 4. 수정 B — 평가 체인과 속도 (같은 커밋으로 학습 전에 함께 구현)

### B1. 그래프 모드 매개변수 (`fine_tuning/error_note/v17_eval.py`)
- params `eval_engine_mode` ∈ {`eager`, `cuda_graph`}. 보호 파일은 고치지 않고, v17 평가 경로에서 vLLM `LLM` 생성 인자만 감싸 `enforce_eager`를 정한다.
- `[사용자 2026-11-17]` 기본 절차: B2의 검증을 `cuda_graph`로 먼저 실행하고, 통과하면 900 평가를 `cuda_graph`로 고정한다.
  실패하면 같은 검증을 `eager`로 다시 실행해 통과한 쪽으로 고정한다. 이 선택은 평가 체인 안에서 자동으로 하고, 사용자 확인을 다시 기다리지 않는다.
  선택 결과(모드, 실패 사유, 각 검증 영수증 SHA)를 사전등록 전에 봉인한다.
- 실제 엔진 설정(`enforce_eager`, compilation/cudagraph 설정, KV 토큰 수)을 엔진에서 읽어 결과 기록에 남긴다. 보호 파일의 `describe()`가 적는 `enforce_eager: True`를 그대로 믿지 않는다.
- protocol 식별자에 "B2 실행 방식 변경(eager→graph)"을 별도 필드로 기록한다. B2와 생성 결과가 비트 단위로 같다고 주장하지 않는다.

### B2. 최종 모델 기준 평가 엔진 검증 (`eval-engine-validation` 단계)
- 학습 결과 영수증 확인 직후, **최종 비병합 모델**로 실행한다(F0는 조정층 값이 0이라 그래프 모드의 조정층 적용을 증명하지 못함).
- 검사 항목:
  1. PF5(기존 `lora_preflight` 증폭 비교)를 선택한 모드에서 통과. 조정층·Merger·시각 훅이 그래프 경로에서 실제 적용되는지 확인.
  2. 외부 성능 전용 16문항에서 eager 대비 첫 토큰 구간 확률 차이가 기존 동기화 기준(`VLLM_SYNC_THRESHOLD`) 이내.
  3. 실제 KV 토큰 수를 다시 읽는다(그래프가 메모리를 추가로 씀).
  4. 처리량: ① 장문 확인(EOS 무시로 32,768 문맥 관측, 선점 0) ② 실제 길이 측정(성능 16문항을 B2 원본 출력 길이 분포의 고정 분위수 길이로 강제, 진단 전용).
     단계별 샘플링·패널티 CPU 시간도 진단으로 기록한다(패널티 계산은 바꾸지 않음).
- 그래프 검증이 실패하면 900 평가 **시작 전에** eager로 확정한다. 평가 도중 모드를 바꿔 이어 붙이지 않는다(다른 실행으로 취급).

### B3. 칸 수를 실제 KV로 계산
- 상수 `SLOTS = 8`을 `칸 수 = 내림(0.9 × 실측 KV ÷ 40,960)`으로 바꾼다(최악의 경우에도 선점 없음 보장, 기존 용량 규칙 유지). 검증 영수증의 KV 값으로 계산·기록한다.
- 16·32칸처럼 용량 규칙을 넘는 동시 수는 쓰지 않는다.

### B4. 제출 순서
- 순서 키 `sha256("v17-eval-order:" + 문항ID)`를 v17 평가 경로가 vLLM에 요청을 넣는 지점에 적용한다(보호 파일의 정렬은 그대로 두고 제출 지점에서 재배열).
  이미지를 한꺼번에 메모리에 올리지 않는 방식으로 구현한다.
- 재개 시에도 같은 순서로 남은 문항만 넣는다. 실제 제출 순서 해시를 결과에 기록하고 검사한다.
- seed·샘플링·문항 정의는 순서와 무관하다.

### B5. 예상 시간과 종료 한도 분리

- 종료 한도: `[사용자 2026-11-17]` **실제 길이 측정 처리량**을 넣은 기존 보수식(출력 1.5배·시간 1.25배·여유)으로 계산한다.
  장문 확인 처리량은 32K 관측·선점 0 검사와 진단 기록에만 쓴다. 입력으로 쓴 처리량과 근거를 영수증에 기록한다.

  충전이 반영되면 Claude가 정지 시각을 다시 계산해 늘린다.
